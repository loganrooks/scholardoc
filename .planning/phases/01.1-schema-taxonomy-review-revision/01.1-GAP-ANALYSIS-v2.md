# Phase 1.1 Gap Analysis v2: Structural Schema Review
# Non-Conservative Analysis -- Corpus Phenomena as Must-Handle Cases

**Date:** 2026-02-19
**Corpus:** ~5,272 pages, 15 texts, ~85 distinct phenomena in 9 categories (139 instances across texts)
**Schema version assessed:** Post-Phase 1.1 (v2.0.0) -- all 5 plans
**Methodology:** NON-CONSERVATIVE

---

## Methodology

The v1 gap analysis (dated 2026-02-19) assessed the Phase 1.1 schema against the corpus of structural phenomena and concluded that zero gaps are blocking, all degraded gaps are covered by the `GTElement.extra="allow"` escape hatch, and Phase 1.2 is "conditional -- beneficial but NOT required." That analysis was methodologically conservative: it asked "can the schema represent this phenomenon at all?" and when the answer was "yes, via extra fields and tags," it declared the gap non-blocking.

This v2 analysis takes the opposite stance. Every phenomenon in this corpus is a **first-class use case**. If 30% of the corpus pages (~1,583 pages across Vilna Shas, Mikraot Gedolot, and Koren Talmud) are RTL multi-layer commentary in Rashi script, then RTL directionality and script variant distinction need dedicated schema models, not ad-hoc extra fields. If Derrida's dual-column/dual-register texts comprise 7 of 15 books in the corpus (Glas, Circumfession, Of Hospitality, Tympan, Margins of Philosophy, and partially Glas's influence on Gibbs), then column/register identity needs first-class modeling. The schema should be **designed for these texts**, not merely tolerant of them.

The assessment framework assigns each phenomenon one of four ratings:
- **Full**: Schema models this phenomenon with dedicated structure. No changes needed.
- **Partial-Structural**: Schema can represent it but through workarounds (extra fields, tags, implicit derivation). A structural fix is needed because the workaround fails to capture the phenomenon's semantics, forces annotators into ad-hoc conventions, or prevents downstream consumers from querying the data without knowledge of the workaround.
- **Partial-Adequate**: Schema represents it well enough that a structural fix would be over-engineering. The workaround is clean, discoverable, and does not burden annotators.
- **None**: Schema cannot represent this phenomenon at all.

For every **Partial-Structural** or **None** rating, a **Structural Fix Proposal (SFP)** follows with: (1) model/enum change, (2) why extra fields are insufficient, (3) Pydantic-style sketch, (4) corpus texts that benefit, (5) impact on Phase 1.1 plans.

## Schema Capabilities Inventory

### Current Schema (v1.0.0) -- What Exists in Code Today

**Region** (spatial.py): `label: SpatialLabel` (17 values), `bbox: BBox`, `text: str|None`, `text_anchors: list[str]`, `semantic_labels: list[SemanticType]`, `reading_order_index: int|None`. No children, no continuation flags, no semantic_element_ids.

**SpatialLabel** (17): TEXT_BLOCK, FOOTNOTE_AREA, ENDNOTE_AREA, PAGE_HEADER, PAGE_FOOTER, PAGE_NUMBER, SECTION_HEADER, TITLE, BLOCK_QUOTE, LIST_ITEM, TABLE, FIGURE, CAPTION, FORMULA, MARGINAL_NOTE, BIBLIOGRAPHY_AREA, FOOTNOTE_CONTINUATION.

**SemanticType** (9): FOOTNOTE, ENDNOTE, CITATION, BIBLIOGRAPHY_ENTRY, SECTION, SOUS_RATURE, CROSS_REFERENCE, MARGINAL_REFERENCE, PAGE_NUMBER_ANNOTATION.

**FormattingType** (6): BOLD, ITALIC, UNDERLINE, STRIKETHROUGH, SMALL_CAPS, SUPERSCRIPT. No SUBSCRIPT, no MONOSPACE.

**FormattingAnnotation**: formatting_type, page, region_id, char_offset, char_length, text. No language field.

**Semantic models**: Footnote, Endnote (separate), Citation (uses CitationType 7-value enum conflating format with reference system), BibEntry (with ParsedCitation), Section, SousRature, CrossReference, MarginalReference (uses MarginalRefType 4-value enum), PageNumberAnnotation.

**PageQuality**: scan_quality (low/medium/high), difficulty (easy/medium/hard). Two categorical fields, no numeric metrics.

**PageGT**: page_index, page_label, dimensions, regions, reading_order, quality, verifications. No section_context, no page_dependency.

**DocumentGT**: schema_version, document_id, source, page_range, elements, formatting, structure, relationships (FootnoteLink/CitationBibLink), config_profile, verifications. No note_schemas, no citation_style.

## Category 1: Dual/Multi-Register Layouts (8 phenomena)

| # | Phenomenon | v2 Rating | Mechanism | Corpus Impact |
|---|-----------|-----------|-----------|---------------|
| 1.1 | Asymmetric dual-column (Glas) | **Partial-Structural** | Region bbox per column, but no column/register identity | Glas ~260pp |
| 1.2 | Horizontal register division (Circumfession) | **Partial-Structural** | Region bbox for upper/lower, but no register concept linking regions to reading streams | Circumfession ~400pp |
| 1.3 | Facing-page layout (Of Hospitality) | **Partial-Structural** | PageDependency for page pairs, but no register mapping across facing pages | Of Hospitality ~170pp |
| 1.4 | Vertical column separation (Tympan) | **Partial-Structural** | Region bbox per column, same issue as 1.1 | Tympan ~16pp |
| 1.5 | Central Gemara + multi-layer commentary (Vilna Shas) | **Partial-Structural** | Commentary.source + Region bbox, but no register model for the spatial-semantic layout convention | Vilna Shas ~600pp |
| 1.6 | Variable-geometry commentary (Mikraot Gedolot) | **Partial-Structural** | Region bbox + Commentary.source, same register gap | Mikraot Gedolot ~700pp |
| 1.7 | Bilingual side-by-side (Koren, Gibbs) | **Partial-Structural** | Region + FormattingAnnotation.language, but no register linking language-direction-author as a first-class concept | Koren ~449pp, Gibbs ~400pp |
| 1.8 | Central text + peripheral apparatus (Gibbs) | **Partial-Structural** | Commentary model + Region bbox, same register gap | Gibbs ~400pp |

### Analysis

The v1 analysis rated 1.2, 1.3, 1.5, 1.6, 1.7, 1.8 as "Full" and 1.1, 1.4 as "degraded." This was misleading. ALL eight phenomena share the same fundamental gap: **the schema has no concept of a register or column identity as a first-class entity**.

Consider what an annotator must do to represent Glas (1.1) in the current schema:
1. Create two Region objects with bboxes for left and right columns.
2. Add `tags: ["column:left", "author:hegel"]` and `tags: ["column:right", "author:genet"]` to each.
3. Hope that every downstream consumer knows to look in `tags` for this critical structural information.

This is not annotation; it is improvisation. The tags are unvalidated strings. There is no schema enforcement that a "column:left" tag exists. There is no way to query "give me all regions in the Hegel register" without string matching on ad-hoc tag values. There is no model linking the register to its metadata (author, language, reading direction, position convention).

The same pattern repeats across ALL eight phenomena. Commentary.source handles attribution for Talmudic texts (1.5, 1.6), but Commentary is a semantic element -- it does not model the spatial layout convention that positions Rashi in the inner margin and Tosafot in the outer margin. FormattingAnnotation.language handles bilingual cases (1.7), but language is a property of individual spans, not a property of the spatial column/register that those spans belong to.

**Corpus impact:** All 8 phenomena affect at least ~2,995 pages (Glas 260 + Circumfession 400 + Of Hospitality 170 + Tympan 16 + Vilna Shas 600 + Mikraot Gedolot 700 + Koren 449 + Gibbs 400). That is **57% of the entire corpus**. This is not an edge case.

## Category 3: Typography and Semantic Encoding (9 phenomena)

| # | Phenomenon | v2 Rating | Mechanism | Corpus Impact |
|---|-----------|-----------|-----------|---------------|
| 3.1 | Register-specific typography | **Partial-Structural** | FormattingAnnotation per region, but no font/typeface model | Circumfession ~400pp |
| 3.2 | Typographic voice separation | **Partial-Structural** | Same gap -- typeface identity is the semantic signal | Of Hospitality ~170pp |
| 3.3 | Differential typeface registers | **Partial-Structural** | Same gap -- columns distinguished BY typeface | Tympan ~16pp |
| 3.4 | Typographic variation as semantic signal | **Full** | FormattingAnnotation (BOLD, ITALIC, etc.) + semantic_labels | Glas ~260pp |
| 3.5 | Typographic emphasis combinations | **Full** | Multiple FormattingAnnotation on overlapping spans | Glas ~260pp |
| 3.6 | Complex typographic hierarchy | **Full** | FormattingAnnotation for decoration + Section.level for hierarchy | Margins ~320pp |
| 3.7 | Multi-typeface semantic encoding (Rashi vs square) | **Partial-Structural** | No script variant model; BCP 47 cannot distinguish Rashi from square Hebrew | Vilna Shas ~600pp, Mikraot Gedolot ~700pp |
| 3.8 | Typography as hierarchical indicator | **Full** | FormattingAnnotation + Section.level + extra fields | Mikraot Gedolot ~700pp |
| 3.9 | Color-coded elements | **Partial-Structural** | No color model at all; FormattingType has no COLOR value | Koren ~449pp |

### Analysis

**3.1 / 3.2 / 3.3 -- Typeface-as-register-signal:**

The v1 analysis rated these as "degraded" and suggested `Region.tags: ["author:bennington", "typeface:serif-9pt"]`. This is inadequate for several reasons:

1. **Annotator burden:** Every annotator must independently invent tag conventions for typeface identity. There is no validation, no schema documentation, no autocomplete support.
2. **Query opacity:** Downstream consumers cannot query "all regions with Bennington's typeface" without knowing the exact tag string the annotator used.
3. **The register gap compounds this.** If registers had first-class identity (SFP-1), typeface association would be a register property, not per-region tags.

However, the typeface gap is partially subsumed by the register proposal. If a LayoutRegister model includes `typeface_convention: str | None`, then the per-region typeface identity is inherited from the register. This reduces the standalone urgency of a typeface model.

**3.7 -- Multi-typeface semantic encoding (Rashi script vs square Hebrew):**

This is the most structurally significant typography gap. In Talmudic texts, the typeface IS the semantic signal:
- **Square Hebrew (block script)** = Gemara (Babylonian Talmud text, Aramaic/Hebrew mix)
- **Rashi script** = Rashi's commentary and most other commentators (Hebrew/Aramaic)

This distinction spans ~1,300 pages of the corpus (Vilna Shas + Mikraot Gedolot). BCP 47 cannot express it: both are "he-Hebr" (Hebrew in Hebrew script). The distinction is typographic, not linguistic or script-systemic.

The v1 workaround (`Commentary.source="Rashi"` correlates with script type) is valid for ATTRIBUTION but not for VISUAL ANNOTATION. An annotator marking ground truth for a region extraction task needs to annotate "this region uses Rashi script" independently of who wrote it, because:
- Some commentators (Ibn Ezra, Ramban) use square script, not Rashi script
- The script type is the visual detection target; the commentary source is the semantic interpretation
- Evaluation metrics for OCR performance need to stratify by script type, not by attributed author

**3.9 -- Color-coded elements:**

The v1 analysis rated this as "nice-to-have" because "color as semantic signal is specific to one text (Koren)." But Koren Talmud Bavli is 449 pages -- nearly 9% of the corpus. In Koren, color encodes:
- Gemara text (one color)
- Mishnah text (another color)
- Commentary attribution (color-coded by commentator)
- Translation emphasis (color signals literal vs interpretive translation)

A schema that cannot annotate "this text span is rendered in color X, which means Y" forces annotators to use `extra: {"color": "#FF0000", "color_semantic": "gemara_text"}` -- an unvalidated, undiscoverable ad-hoc convention. For a text that represents 9% of the corpus, this is not acceptable.

## Category 5: Foreign Language and Script Systems (9 phenomena)

| # | Phenomenon | v2 Rating | Mechanism | Corpus Impact |
|---|-----------|-----------|-----------|---------------|
| 5.1 | Italicized foreign passages | **Full** | FormattingAnnotation ITALIC + language tag | Margins ~320pp |
| 5.2 | Greek/Latin in running text | **Full** | FormattingAnnotation.language="el"/"la" per span | Margins, Being and Time |
| 5.3 | Interpolated German terms | **Full** | FormattingAnnotation.language="de" | Being and Time ~590pp |
| 5.4 | Mixed language/transliteration | **Full** | Multiple language tags on overlapping spans | Gibbs ~400pp, Koren ~449pp |
| 5.5 | Rashi script commentary | **Partial-Structural** | language="he" + Commentary.source, but no script variant | Vilna Shas ~600pp, Mikraot Gedolot ~700pp |
| 5.6 | RTL with nested complexity | **Partial-Structural** | Language implies direction, but no explicit text_direction | Mikraot Gedolot ~700pp |
| 5.7 | RTL text directionality | **Partial-Structural** | Same gap as 5.6 | All Hebrew texts ~1,749pp |
| 5.8 | Script differentiation | **Partial-Structural** | Same gap as 3.7 (cross-reference) | Vilna Shas ~600pp |
| 5.9 | Multilingual apparatus | **Full** | FormattingAnnotation.language per span in Note/Commentary | Of Grammatology, Specters |

### Analysis

**5.5 / 5.8 -- Script variant distinction:** Covered under Category 3, phenomenon 3.7. The script variant gap affects ~1,300 pages and requires a dedicated model (see SFP-3).

**5.6 / 5.7 -- Text directionality:**

The v1 analysis said: "Text direction is derivable from language tags in most cases." This is precisely the kind of conservative reasoning v2 rejects. The problems with deriving direction from language tags:

1. **Derivation is consumer burden.** Every downstream consumer must implement BCP 47 -> direction mapping. The schema should declare the direction explicitly so consumers can read it directly.
2. **Bidi regions have no single direction.** A region containing Hebrew with inline Latin citations is neither pure RTL nor pure LTR. The base direction determines rendering order, but `language="he"` on the region does not capture that the region is BIDI with an RTL base.
3. **Ground truth evaluation requires explicit direction.** When evaluating whether an extractor correctly detected reading direction, you need the ground truth direction annotated, not derived. The annotation IS the truth; derivation introduces error.
4. **Page-level base direction is essential for layout analysis.** A layout model processing a Vilna Shas page needs to know it's an RTL page before processing region positions. Deriving this from individual span language tags is backwards.

**Corpus impact:** ~1,749 pages across Vilna Shas (~600), Mikraot Gedolot (~700), and Koren (~449) are RTL-base-direction pages. That is **33% of the corpus**.

**Standard philosophy texts benefit too:** Being and Time contains inline Greek (5.2) that is LTR within an LTR base, but explicit direction annotation enables systematic evaluation of multi-script extraction. Of Grammatology's multilingual apparatus (French, German, Italian in footnotes) benefits from explicit language + direction annotation per span.

### Analysis

**6.6 -- Catchword anchoring (Dibbur Ha-Matchil):**

The v1 analysis rated this "nice-to-have" and said `Commentary.reference_system=CUSTOM` is adequate. Under non-conservative scrutiny:

Catchword anchoring is the PRIMARY reference mechanism for Talmudic commentary. Every Rashi and Tosafot entry on every page of Vilna Shas and Mikraot Gedolot uses dibbur ha-matchil to anchor commentary to the source text. This is not a rare reference system -- it is THE reference system for ~1,300 pages of the corpus.

Using `CUSTOM` for the single most common reference system in a third of the corpus is backwards. The ReferenceSystem enum has 12 values including DIELS_KRANZ (for Pre-Socratic fragments, appearing in zero pages of the corpus) and LEGAL (for legal citations, appearing in zero pages). But CATCHWORD, which appears on ~1,300 pages, uses `CUSTOM`? This is a taxonomy oversight.

Adding `CATCHWORD = "catchword"` to ReferenceSystem is a one-line enum addition. It properly names the most common reference mechanism in the Hebrew/Aramaic portion of the corpus.

**6.11 -- Traditional positioning conventions:** Rated Partial-Adequate because the convention (Rashi top-right, Tosafot outer margin) is extraction/layout knowledge, not annotatable ground truth. The schema correctly captures the result (Commentary.source + Region.bbox) without needing to encode the convention itself.

### Analysis

**7.6 / 7.7 -- Back-of-book index:**

The v1 analysis said: "Only 2 texts in the corpus have significant indexes... The UNKNOWN label + tags adequately represents it." Under non-conservative lens:

Of Grammatology's index spans pages 413-444 (31 pages). Being and Time's index spans pages 575-590 (15 pages). Combined: 46 pages of index content in two of the most important texts in the corpus.

Using `UNKNOWN` for a structural element that appears in standard scholarly texts is a schema design failure. Every scholarly monograph has an index. TOC_AREA exists because tables of contents are standard. INDEX_AREA should exist for the same reason.

The argument is not about page count (46 pages is small). It is about:
1. **Semantic clarity.** UNKNOWN means "we don't know what this is." An index is a well-understood scholarly apparatus. Labeling it UNKNOWN is factually wrong.
2. **Layout detection evaluation.** If you want to evaluate whether an extractor correctly identifies index regions, you need an INDEX_AREA label. UNKNOWN + tags breaks standard evaluation pipelines that operate on enum values.
3. **Consistency.** TOC_AREA and BIBLIOGRAPHY_AREA exist as standard scholarly apparatus labels. INDEX_AREA completes the set.

| 9.9 | Text-based PDF | **Full** | PageQuality.is_scan=false | Loeb Aristotle |

### Analysis

**9.1 -- Handwritten annotations:**

The v1 analysis rated this "degraded" and noted it appears in only one text (Margins of Philosophy, 4 pages). Under non-conservative lens:

Even at 4 pages, handwritten annotations represent a real phenomenon that the schema cannot model: the location, content, and distinction between printed and handwritten content on a page. However, 4 pages out of 5,272 is genuinely rare (0.08%). The structural fix would be a `ContentLayer` concept (printed vs handwritten) on Region. This is architecturally lightweight but serves an extremely narrow use case.

**Assessment:** Partial-Structural but Tier 3 (consider deferring). The phenomenon is real but genuinely rare in this corpus. A `content_layer: Literal["printed", "handwritten"] | None` field on Region would suffice.

**9.3 -- Mathematical/symbolic notation:** Rated Partial-Adequate. Mathematical notation in Gibbs is sparse (~20 pages) and mostly representable via FORMULA regions and SUPERSCRIPT/SUBSCRIPT formatting. Inline math within running text is a narrow gap that does not justify a structural fix.

**9.7 -- Intentional parallel enrichment:** Rated Partial-Adequate. This is a literary/hermeneutic concept ("these texts are designed to be read together for enriched meaning"), not an annotatable structural feature. ## Structural Fix Proposals -- Detailed

### SFP-1: LayoutRegister Model + Region.register_id

**Addresses gaps:** G1, G2 (partial)
**Corpus impact:** ~2,995 pages across 8+ texts (57% of corpus)
**Why extra fields are insufficient:** Extra fields and tags provide no validation, no queryability, no schema documentation, and no link between a spatial region and a document-level concept (register metadata: author, language, reading direction, position convention). Every annotator invents their own tag strings. Every consumer must reverse-engineer those strings.

**Proposed model/enum changes:**

```python
class LayoutRegister(BaseModel):
    """A named reading stream or column in a multi-register document.

    Provides first-class identity for parallel text streams, commentary
    layers, bilingual columns, and multi-register layouts. Each register
    maps to a set of regions across pages.
    """
    register_id: str = Field(description="Unique register identifier (e.g., 'hegel', 'genet', 'rashi')")
    name: str = Field(description="Human-readable register name")
    author: str | None = Field(default=None, description="Author or attributed source")
    language: str | None = Field(default=None, description="Primary BCP 47 language tag")
    text_direction: Literal["ltr", "rtl"] | None = Field(
        default=None, description="Base text direction for this register"
    )
    position_convention: str | None = Field(
        default=None,
        description="Layout convention (e.g., 'left_column', 'upper_register', 'inner_margin', 'central')"
    )
    typeface_convention: str | None = Field(
        default=None, description="Expected typeface family (e.g., 'rashi_script', 'square_hebrew', 'serif_9pt')"
    )
```

On Region, add:
```python
    register_id: str | None = Field(
        default=None, description="LayoutRegister this region belongs to"
    )
```

On DocumentGT, add:
```python
    registers: list[LayoutRegister] = Field(
        default_factory=list, description="Named reading streams / column identities in this document"
    )
```

**Phase 1.1 plan impact:**
- Plan 01: No change (LayoutRegister is a new model, not an enum change)
- Plan 02: Add `register_id: str | None` to Region in spatial.py; add LayoutRegister to semantic.py or a new registers.py
- Plan 03: Add `registers: list[LayoutRegister]` to DocumentGT in document.py
- Estimated additional complexity: Moderate. Two field additions + one new model (~30 lines).

**Texts that benefit:**
- Glas: Hegel/Genet columns with independent footnote zones
- Circumfession: Bennington (upper) / Derrida (lower) registers
- Of Hospitality: Dufourmantelle (verso) / Derrida (recto) facing pages
- Tympan: Left/right counter-text columns
- Vilna Shas: Central Gemara + Rashi (inner margin) + Tosafot (outer margin)
- Mikraot Gedolot: Central Torah + variable commentator blocks
- Koren Talmud: Hebrew/English bilingual columns
- Gibbs: Central text + peripheral talmudic-evocation apparatus

### SFP-2: Text Direction on Region and Page

**Addresses gaps:** G5, G12
**Corpus impact:** ~1,749 pages across all Hebrew/Aramaic texts (33% of corpus)
**Why extra fields are insufficient:** Text direction is a fundamental layout property required for correct rendering, reading order interpretation, and OCR evaluation. Storing it in `extra: {"text_direction": "rtl"}` means:

On PageGT:
```python
    base_direction: Literal["ltr", "rtl"] | None = Field(

```

### SFP-3: Script Variant Enum

**Addresses gaps:** G3
**Corpus impact:** ~1,300 pages across Vilna Shas and Mikraot Gedolot
**Why extra fields are insufficient:** Script variant is the primary visual classifier for Talmudic text regions. Using `extra: {"script_variant": "rashi"}` means no enum validation, no documented set of values, and no standard way for annotators to express what is the single most important typographic distinction in Hebrew scholarly texts.

BCP 47 cannot express this: both Rashi script and square Hebrew are "he-Hebr" (Hebrew language, Hebrew script system). The distinction is within the script system -- it is a font/typeface variant, not a script change. But it is a STANDARDIZED variant with centuries of typographic tradition.

**Proposed model/enum changes:**

```python
class ScriptVariant(str, Enum):
    """Script variant within a writing system, for cases where
    BCP 47 script subtags are insufficient.

    Primary use: distinguishing Rashi script from square (block) Hebrew,
    which both fall under BCP 47 'Hebr' but carry distinct semantic meaning
    in Talmudic typography.
    """
    SQUARE_HEBREW = "square_hebrew"       # Standard block Hebrew (Gemara, biblical text)
    RASHI_SCRIPT = "rashi_script"         # Rashi/semi-cursive (commentary tradition)
    NASTALIQ = "nastaliq"                 # Persian/Urdu calligraphic variant (future)
    NASKH = "naskh"                       # Standard Arabic print (future)
    FRAKTUR = "fraktur"                   # German blackletter (historical texts)
    CUSTOM = "custom"                     # Project-specific variant
```

On FormattingAnnotation, add:
```python
    script_variant: ScriptVariant | None = Field(
        default=None,
        description="Script variant for this span (when BCP 47 script subtag is insufficient)"
    )
```

**Phase 1.1 plan impact:**
- Plan 01: Add ScriptVariant enum to labels.py
- Plan 02: Add `script_variant` field to FormattingAnnotation in formatting.py
- Estimated additional complexity: Minimal. One enum (~10 lines) + one field addition.

**Texts that benefit:**
- Vilna Shas (~600pp): Every page uses both square Hebrew (Gemara) and Rashi script (commentaries)
- Mikraot Gedolot (~700pp): Biblical text in square, commentaries in Rashi script
- Koren Talmud (~449pp): Uses square and Rashi script with color coding

## Recommendations

### Tier 1 -- Must Adopt (schema is fundamentally under-designed without these)

**SFP-1: LayoutRegister + Region.register_id**
- Rationale: 57% of corpus pages use multi-register layouts. The schema's inability to name, describe, and link registers to regions is the single largest structural gap. Every other register-related gap (typeface-as-register-signal, register-specific footnotes, bilingual column pairing) is partially addressed by giving registers first-class identity.
- Effort: One new model + two field additions (~26 lines)

**SFP-2: Text direction on Region and Page**
- Rationale: 33% of corpus is RTL. Text direction is a fundamental layout property that must be explicit for ground truth annotation, not derived from language tags.
- Effort: Two field additions (2 lines)

**SFP-3: ScriptVariant enum**
- Rationale: ~1,300 pages rely on Rashi-vs-square distinction as the primary visual classifier. This is the typographic equivalent of bold-vs-italic in Western texts -- it must be a first-class annotation target.
- Effort: One enum + one field (12 lines)

### Tier 2 -- Should Adopt (significantly improves schema for core use cases)

**SFP-6: CATCHWORD in ReferenceSystem**
- Rationale: Most common reference mechanism in ~1,300 pages of Hebrew texts. One-line addition.
- Effort: 1 line

**SFP-4: Color annotation**
- Rationale: 449 pages (9% of corpus) use color semantically. Structured color annotation enables evaluation of color extraction accuracy.
- Effort: 1 enum value + 2 fields (3 lines)

**SFP-5: INDEX_AREA spatial label**
- Rationale: Standard scholarly apparatus in 2 major texts. UNKNOWN is semantically wrong.
- Effort: 1 line

### Tier 3 -- Consider Deferring (real but narrow gaps)

**SFP-7: Content layer on Region**
- Rationale: Real phenomenon, genuinely rare (4 pages). The field addition is trivial but serves an extremely narrow use case.
- Effort: 1 line. Include if convenient during Plan 02; omit without loss.

**G8 (synchronized column flow):** Analysis concern, not annotation. Addressed as register-level metadata if SFP-1 is adopted.

**G10 (inline math):** Sparse phenomenon (~20 pages). FORMULA + SUPERSCRIPT/SUBSCRIPT adequate.

**G11 (parallel enrichment):** Literary interpretation, not annotation.

### What v1's "Extra Fields Cover It" Approach Missed

1. **Scale matters.** When a phenomenon affects 57% of the corpus (registers) or 33% (RTL direction), it is not an edge case that extra fields can cover. It is a core design requirement.

2. **Annotator experience matters.** Extra fields require annotators to invent ad-hoc conventions, remember undocumented tag strings, and hope that downstream consumers know how to find their annotations. Schema-validated fields are discoverable, documented, and auto-completable.

3. **Evaluation pipeline compatibility matters.** Standard GT evaluation tools operate on enum values, model fields, and typed data. They cannot query `extra: {"text_direction": "rtl"}` without custom code. Every gap addressed by extra fields is a gap that breaks standard evaluation workflows.

4. **The corpus defines the schema.** v1 treated the schema as a pre-existing design that the corpus must fit into. v2 treats the corpus as the requirements document that the schema must be designed around. If 30% of pages are RTL multi-layer commentary in Rashi script, the schema should have dedicated models for RTL direction, multi-layer registers, and Rashi script -- not because these are nice enhancements, but because these are the texts the schema exists to serve.

5. **Taxonomy consistency matters.** v1 accepted DIELS_KRANZ and LEGAL in ReferenceSystem (zero corpus pages) while leaving CATCHWORD (~1,300 pages) as CUSTOM. It accepted TOC_AREA while leaving INDEX_AREA as UNKNOWN. These are taxonomy inconsistencies that undermine the schema's credibility as a "universal annotation taxonomy."
