# Phase 1.1: Schema Taxonomy Review & Revision - Context

**Gathered:** 2026-02-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Redesign the label taxonomy from first principles: organize labels by downstream evaluation task, fix spatial/semantic conflation, decompose CitationType into orthogonal axes, replace categorical ScanQuality with measurable attributes, clarify the page→region→text→span data hierarchy, and address all identified structural tensions in the schema.

The schema serves MULTIPLE consumers (not just ScholarDoc): layout detection, OCR quality evaluation, citation extraction, spellcheck calibration, terminology extraction, document structure analysis, annotator training, and active learning pipelines.

## Implementation Decisions

Decisions are categorized by depth of discussion:
- **DECIDED** — Thoroughly discussed with user, direction locked
- **RECOMMENDED** — Preliminary recommendation from analysis, research may refine

### Note Consolidation [DECIDED]

**Decision**: Consolidate Footnote and Endnote into a single **Note** model with differentiating properties.

- Single `Note` model replaces both `Footnote` and `Endnote`
- `placement` field: `page_bottom | end_of_chapter | end_of_book | margin` (NOT "inline" — not a real scholarly convention)
- `scope` field for numbering reset boundary: `page | chapter | section | essay | document`
- `note_source`: `author | translator | editor`
- **Two marker locations**: `body_marker` (where reference appears in text) + `content_marker` (where note content begins, especially important for endnotes)
- **ContentSpan gets char_offset/char_length**: For endnotes sharing a single region, individual notes need character-level positioning within the shared ENDNOTE_AREA region
- **Nesting via spatial reference**: Notes-within-notes (e.g., endnote marker in a footnote) are flat elements in DocumentGT — nesting is implicit because the inner note's body_marker references a region that's within the outer note's content
- **NoteSchema at document level**: Marker type (arabic, roman, alphabetical, symbolic, custom), symbol sequence, reset boundary, placement, note source — a document can have MULTIPLE note schemas simultaneously
- **SemanticType**: FOOTNOTE + ENDNOTE consolidated to just `NOTE`

**Rationale**: The differences between footnotes and endnotes are PROPERTIES (placement, scope, numbering) not TYPES. Consolidation simplifies Phase 2 extractors, Phase 3 evaluation (stratify by property), and Phase 4 annotation UI. Handles complex scenarios: mixed translator footnotes + author endnotes, chapter-scoped endnotes, multi-page footnotes, nesting.

### Page/Document Architecture [DECIDED]

**Decision**: Keep hybrid page/document split but make linkage rigorous.

- **PageGT** = "What can you SEE on this page?" — regions with bboxes, spatial labels, text
- **DocumentGT** = "What does it MEAN across the document?" — semantic elements (notes, citations, sections, commentary)
- **Linkage**: Full addresses `{page: int, region_id: str}` always used together
- **Canonical text source**: Region.text in PageGT is source of truth. ContentSpan references by location (page + region_id + char_offset + char_length) rather than duplicating text
- **Bidirectional references**: Region gets `semantic_element_ids: list[str]` back-referencing which DocumentGT elements point to it
- **Cross-reference validation**: Validator checks all region_id references resolve to actual regions in corresponding PageGT files

**Design principle**: Design for clarity first, create adapters for external model interoperability. We do NOT need to match DocLayNet/PubLayNet label sets — we can create translators between their output schemas and ours.

### Cross-Page Relationships [DECIDED]

**Decision**: Explicit continuation modeling at region level + page-level dependency metadata.

- **Region-level flags**: `is_continuation: bool` (continues from previous page) + `continues_to_next: bool` (continues to next page) on every Region
- **Page-level dependency metadata**: Each page declares its dependencies:
  - `continues_from_previous: bool` — some content is a continuation
  - `continues_to_next: bool` — some content continues forward
  - `unresolved_markers: list[str]` — body markers with no note on this page (endnote refs)
  - `orphan_continuations: list[str]` — note content with no marker on this page
- **Purpose**: Pages are self-describing for partial GT annotation (page sampling). When annotating page 46 in isolation, the metadata tells you "this page depends on page 45" before you discover it from the content.
- **Covers**: paragraph continuations, sentence continuations, footnote continuations, table continuations, figure-caption splits across pages

### Section Context on Pages [DECIDED]

**Decision**: Lightweight `section_context` on PageGT.

- Each page carries its hierarchical section path: `[{section_id, title, level}]`
- For pages spanning section boundaries: `starts_on_this_page` / `ends_on_this_page` flags
- Canonical section hierarchy lives in DocumentGT. Page-level context is denormalized for self-describing pages
- Supports partial GT annotation: annotator sees "Page 45 — Chapter 3: Being-in-the-World" without loading DocumentGT

### Commentary Apparatus [DECIDED]

**Decision**: Design commentary model in this phase (not deferred).

- Commentary is fundamentally different from notes: organized by passage reference, not by markers
- Separate model from Note: `Commentary` with source (who wrote it), passage_ref (what it comments on), reference_system (how it locates the passage), target location, content spans
- Handles: critical edition apparatus, Talmud-style multi-layer commentary, editorial commentary
- Multiple commentary layers per passage (Rashi, Tosafot, editor notes, etc.)
- References use external coordinates (Stephanus pages, line numbers) not in-text markers

### Chicago Footnote-as-Citation [DECIDED]

**Decision**: Note can contain Citation elements. Notes and Citations are separate models that can reference shared content regions.

- Chicago NB system: the footnote IS the citation. The note body contains bibliographic reference text.
- A Citation element can reference a region_id that's within a note's content area
- The Note model doesn't need special citation fields — the relationship is spatial (Citation points to the same region as Note content)

### Note Spatial Labels [DECIDED — research validates]

**Decision**: Research phase investigates unified `NOTE_AREA` vs visually-named variants.

- Currently: FOOTNOTE_AREA, ENDNOTE_AREA, FOOTNOTE_CONTINUATION (3 labels)
- Candidate: NOTE_AREA + NOTE_CONTINUATION (2 labels, consistent with semantic consolidation)
- Or: PAGE_BOTTOM_NOTES / NOTE_SECTION (named by visual pattern, not semantic content)
- Research investigates DocLayNet/PubLayNet conventions and whether the visual distinction is meaningful for layout detection
- **Design principle**: We don't need to concede to external model output schemas. We can create translators.

### SpatialLabel Restructuring [RECOMMENDED]

**Preliminary recommendation**: Keep most labels, rename for visual clarity, research borderline cases.

**Current tensions**:
- Some labels named by content (BIBLIOGRAPHY_AREA) rather than visual pattern
- Missing labels: TOC_AREA, ABSTRACT, SIDEBAR, CODE_BLOCK
- Overlap ambiguity: When is SECTION_HEADER also TITLE? When is CAPTION also TEXT_BLOCK?
- Multi-label support: Can a region be both TABLE and FIGURE? Currently single-label

**Proposed direction**:
- Core visual labels (TEXT_BLOCK, PAGE_HEADER, PAGE_FOOTER, TABLE, FIGURE, FORMULA, LIST_ITEM, BLOCK_QUOTE, MARGINAL_NOTE): keep as-is
- Font-feature labels (SECTION_HEADER, TITLE, CAPTION): keep — standard in DocLayNet, visually detectable
- Note labels: consolidate per Note Consolidation decision
- BIBLIOGRAPHY_AREA: research whether visually distinguishable enough for its own label vs TEXT_BLOCK + semantic annotation
- Consider adding: TOC_AREA, ABSTRACT (both have distinctive visual patterns)
- Consider: UNKNOWN/AMBIGUOUS label for uncertain annotations

**Research needed**: DocLayNet/PubLayNet label comparison, multi-label vs hierarchical labels, adapter/mapping design for external models.

### CitationType Decomposition [RECOMMENDED]

**Preliminary recommendation**: Decompose into three orthogonal axes.

**Current tension**: 7 values conflate citation format, reference system, and style.

**Proposed axes**:
1. **CitationFormat** (per-citation, how it appears in text):
   - PARENTHETICAL: "(Smith, 2020)" or "(Rep. 267a)"
   - NUMERIC: "[1]" or superscript "¹"
   - INLINE_AUTHOR: "Smith argues..."
   - NOTE_BASED: Citation IS a footnote (Chicago NB)
   - AUTHOR_TITLE: "Author, Short Title" or work abbreviation

2. **ReferenceSystem** (per-citation, what coordinates locate the passage):
   - STANDARD: Author + Year + Page (default academic)
   - STEPHANUS: Platonic dialogue + page + section letter
   - BEKKER: Aristotelian work + page + column + line
   - AKADEMIE: Kantian work + volume + page
   - PARAGRAPH: § paragraph numbers (Hegel, legal texts)
   - AB_EDITION: A/B edition pages (Kant's first Critique)
   - LINE_NUMBER: Work + line/verse (poetry, some classical texts)
   - CUSTOM: Project-specific system

3. **Citation style** (per-document level): APA, CHICAGO_NB, CHICAGO_AD, MLA, VANCOUVER, etc.

**This eliminates MarginalRefType duplication**: MarginalReference uses the same ReferenceSystem enum. No more separate MarginalRefType with overlapping Stephanus/Bekker values.

**Research needed**: Complete inventory of canonical philosophical reference systems (Hegel §, Being and Time SZ pagination, Phenomenology of Spirit, etc.). Whether there are published standards for these. How translated editions handle reference systems. What other domain-specific systems exist beyond philosophy (legal, biblical, classical).

### ScanQuality Replacement [RECOMMENDED]

**Preliminary recommendation**: Hybrid approach.

- Quick categorical assessment: `overall: low | medium | high` (for fast human annotation)
- Optional numeric metrics: DPI estimate, contrast ratio, skew angle, noise level, OCR confidence (for automated analysis)
- Specific artifact flags: `artifacts: list[str]` — bleed_through, foxing, skew, margin_cropping, water_damage, faded_ink
- `is_scan: bool` — scanned vs born-digital distinction
- Difficulty (currently a separate enum with same problem) gets same treatment: specific difficulty factors instead of EASY/MEDIUM/HARD

### Relationship Modeling [RECOMMENDED]

**Preliminary recommendation**: Embedded references as primary model.

- Drop `DocumentRelationships` as a separate structure
- Note model's marker+content IS the note linkage
- Citation.bib_entry_id IS the citation-bibliography link
- CrossReference already has target_page/target_section_id
- Provide utility function that constructs a relationship graph from embedded references on demand
- Eliminates dual-representation consistency risk (no more FootnoteLink/CitationBibLink duplicating what's already in the elements)

### DocumentType Naming Collision [RECOMMENDED]

**Preliminary recommendation**: Rename labels.py `DocumentType` to `DocumentSectionType` or `DocumentStructuralType`.

- labels.py DocumentType (METADATA, TOC, FRONT_MATTER, BACK_MATTER, NOTE_SCHEMA) = structural sections
- DocumentSource.document_type Literal ("book", "article", ...) = document classification
- These are completely different concepts with the same name — rename the enum to eliminate confusion

### Text Element Model [RESEARCH]

**Key question**: How to represent text properties (formatting, language, script, semantic significance) within regions.

**Current problems**:
- Formatting tracked via separate FormattingAnnotation model (char_offset/char_length into region text)
- Language/script not modeled at all
- SousRature is a semantic element but uses char_offset/char_length like formatting
- No unified way to query "tell me everything about this word"
- Mixed-language text (German + Greek + Latin in philosophy) has no representation

**Options under consideration**:
- **Unified TextSpan**: One span per distinct text segment with all properties (formatting, language, script, semantic_role). Clean to query but forces simultaneous determination.
- **Separate annotation layers**: FormattingLayer, LanguageLayer, SemanticLayer each with their own spans. Supports incremental annotation by different tools/annotators.
- **Hybrid**: Layered storage with unified query API

**Individuation principle**: A new text span starts when ANY property changes. Only spans with non-default properties need annotation.

**SousRature specifically**: Visually identical to strikethrough but philosophically meaningful. Must distinguish regular strikethrough (editor's deletion) from sous rature (Derridean philosophical gesture). Suggests formatting alone is insufficient — need semantic annotation on formatting.

**Other formatting-with-meaning patterns**: Scare quotes as philosophical distancing, emphasis vs translator emphasis (different meanings), em dashes as structural device.

**Research needed**: TEI handling of overlapping annotations, standoff annotation patterns, ALTO/PAGE XML text property models.

### Philosophy-Specific Citation Systems [RESEARCH]

**Key question**: What canonical reference systems exist and how should they be modeled?

**Known systems** (need verification and completion):
- Stephanus pagination (Plato)
- Bekker numbers (Aristotle)
- Akademie edition (Kant)
- § paragraph system (Hegel's Phenomenology of Spirit, also legal texts)
- SZ pagination (Heidegger's Being and Time)
- A/B edition system (Kant's Critique of Pure Reason)

**Research needed**:
- Complete inventory of philosophy-specific reference systems
- Published standards for each (if any)
- How translated editions handle reference systems (some preserve, some don't)
- How the same work gets cited differently across traditions
- Whether ReferenceSystem should be a closed enum or extensible registry
- Other domain-specific systems (legal, biblical, classical, scientific)

### Vocabulary and Language Annotation [RESEARCH]

**Key question**: How to support downstream tasks that depend on word/span-level language and domain classification.

**Use cases driving this**:
- **Spellcheck calibration**: GT marks foreign terms and domain vocabulary so spellcheckers don't flag them as errors
- **OCR escalation**: Pages with high foreign-term density or non-Latin scripts need different/better OCR engines
- **Language-stratified evaluation**: Greek OCR accuracy evaluated separately from English
- **Terminology extraction**: Philosophical terms, foreign terms, technical terms — GT marks these for evaluation
- **Custom vocabulary generation**: GT can produce per-document or per-corpus vocabulary lists for downstream tools

**Schema implications**: Language annotation at the text span level is NOT optional — it's essential for practical pipeline evaluation. Every downstream task that processes text content benefits from knowing the language/domain of each span.

**Research needed**: Language tagging standards (BCP 47), how TEI handles mixed-language text, what granularity of language annotation is practical for human annotators.

## Specific Ideas

### Downstream Evaluation Tasks (driving the taxonomy)

The schema serves multiple evaluation pipelines. Every label should justify itself by supporting at least one:

| Evaluation Task | What GT Annotations It Needs |
|----------------|------------------------------|
| Layout detection (IoU, mAP) | Region bboxes + spatial labels |
| OCR quality (CER/WER) | Correct text per region, language-stratified |
| Reading order accuracy | Ordered region list per page |
| Citation extraction | Citation spans + parsed components + reference system |
| Note linkage correctness | Marker→content connections verified |
| Document structure | Section hierarchy, ToC accuracy |
| Formatting preservation | Char-level formatting annotations |
| Language detection | Language labels per text span |
| Spellcheck calibration | Foreign terms + domain vocabulary marked |
| Named entity recognition | Entity spans + types |
| Terminology extraction | Domain term spans + classification |
| Error diagnosis | Granular annotations distinguishing bbox / label / text / linkage errors |
| OCR escalation decisions | Page complexity signals (foreign terms, quality, formatting density) |
| Annotator training | Inter-annotator agreement via VerificationRecord |

### Page Sampling Considerations

GT won't cover every page of every document. Pages must be self-describing:
- Each page declares its cross-page dependencies
- Unresolved markers and orphan continuations are explicit
- Section context is denormalized onto each page
- An annotation tool can flag: "Page 46 depends on page 45 — include it in the sample?"
- AI agents can identify cross-page signals: no indent (continuation), no marker (orphan footnote), superscript with no corresponding note (endnote reference)

### Endnote Page Representation

For pages that ARE endnote sections:
- One ENDNOTE_AREA (or NOTE_AREA) region per visual block — not per individual endnote
- Individual notes within the block use char_offset/char_length in ContentSpan
- Layout detection sees one region; note extraction uses character positioning
- This is a key difference from footnotes (typically one region per footnote)

### Complex Scenarios the Schema Must Handle

1. Mixed translator footnotes + author endnotes in same edition
2. Chapter-scoped endnote reset in essay collections
3. Symbolic marker sequences with page reset (*, †, ‡, §, ‖, ¶)
4. Multi-page footnotes continuing across page boundaries
5. Endnote markers in footnotes (nesting via spatial reference)
6. Chicago NB: footnote IS the citation
7. Multiple commentary layers on same passage (critical editions)
8. Mixed-language text (German + Greek + Latin insertions)
9. Philosophical formatting (sous rature, scare quotes, emphasis distinctions)
10. Canonical reference systems (Stephanus, Bekker, §, A/B edition, SZ)
11. Pages with incomplete paragraphs/sentences (cross-page continuations)
12. Tables and figures spanning page boundaries
