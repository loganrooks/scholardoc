# Phase 1.1: Schema Taxonomy Review & Revision - Research

**Researched:** 2026-02-18
**Domain:** Pydantic schema redesign for multi-consumer GT annotation taxonomy
**Confidence:** HIGH (schema patterns are well-established; philosophy reference systems and TEI models verified against authoritative sources)

## Summary

Phase 1.1 is a schema redesign phase that restructures the ScholarGT label taxonomy based on user-decided architectural changes. The core changes are: consolidating Footnote/Endnote into a unified Note model (validated by TEI P5's identical approach), adding Commentary apparatus (informed by TEI critical apparatus), decomposing CitationType into orthogonal axes (CitationFormat x ReferenceSystem x citation style), replacing categorical ScanQuality with a hybrid model, adding cross-page relationship modeling, and making pages self-describing for partial annotation.

External research validates every major DECIDED item. TEI P5 uses a single `<note>` element with `@place` attribute to distinguish footnotes/endnotes/marginal notes -- exactly the pattern the user chose. TEI's critical apparatus (`<app>`/`<lem>`/`<rdg>`) provides a mature model for commentary separate from notes. DocLayNet's 11-class taxonomy and its v2 expansion to 17 classes inform which spatial labels are standard and which are missing. BCP 47 language tagging provides the standard for mixed-language text annotation. Pydantic discriminated unions with custom discriminator functions support the extensibility needed.

**Primary recommendation:** Execute changes in dependency order: (1) base models and shared types (LocationRef, BCP47 language), (2) label enums, (3) Note consolidation + Commentary, (4) CitationType decomposition, (5) page-level changes (cross-page, section_context, quality), (6) document-level changes (drop DocumentRelationships), (7) config/validation/examples, (8) comprehensive testing.

### Pattern 1: LocationRef for Consistent Cross-Element Referencing
**What:** Standardized model for referencing a position in the GT corpus
**When to use:** Any semantic element that references a page+region+character position
**Why:** Currently, `page`, `region_id`, `char_offset`, `char_length` are scattered across models inconsistently. LocationRef provides a single reusable type.

```python
# Source: Design decision from CONTEXT.md tension #4
class LocationRef(BaseModel):
    """Reference to a specific location in the GT corpus."""
    page: int = Field(description="0-based page index")
    region_id: str = Field(description="Region ID on the page")
    char_offset: int | None = Field(default=None, description="Character offset within region text")
    char_length: int | None = Field(default=None, description="Length of referenced text span")
```

### Pattern 2: Note Model with Dual Markers
**What:** Consolidated Note replacing Footnote/Endnote with explicit body and content marker locations
**When to use:** Any note-like element regardless of placement
**Why:** TEI P5 uses single `<note>` with `@place`. Differences are properties, not types.

```python
# Informed by TEI P5 <note> element: @place=bottom|end, @resp, @n
class Note(GTElement):
    """A scholarly note (footnote, endnote, marginal note) with marker locations."""
    element_type: Literal["note"] = "note"
    body_marker: LocationRef = Field(description="Where reference marker appears in body text")
    content_marker: LocationRef | None = Field(
        default=None, description="Where note content begins (important for endnotes)"
    )
    content: list[ContentSpan] = Field(description="Content spans (may cross pages)")
    placement: Literal["page_bottom", "end_of_chapter", "end_of_book", "margin"]
    scope: Literal["page", "chapter", "section", "essay", "document"] | None = Field(default=None)
    note_source: Literal["author", "translator", "editor"] | None = Field(default=None)
```

### Pattern 3: Orthogonal Citation Axes
**What:** CitationFormat (how it looks) x ReferenceSystem (what coordinates it uses) x citation style (document-level convention)
**When to use:** Citation elements and MarginalReference elements share ReferenceSystem
**Why:** Current CitationType conflates format and reference system. The 7 values mix "author_date" (a format) with "stephanus" (a reference system).

```python
# Decomposed from current CitationType (7 values -> 2 enums + document-level style)
class CitationFormat(str, Enum):
    PARENTHETICAL = "parenthetical"     # (Smith, 2020)
    NUMERIC = "numeric"                  # [1] or superscript
    INLINE_AUTHOR = "inline_author"      # Smith argues...
    NOTE_BASED = "note_based"            # Chicago NB: footnote IS citation
    AUTHOR_TITLE = "author_title"        # Author, Short Title

class ReferenceSystem(str, Enum):
    STANDARD = "standard"                # Author + Year + Page
    STEPHANUS = "stephanus"              # Plato: dialogue + page + section (e.g., Republic 514a)
    BEKKER = "bekker"                    # Aristotle: page + column + line (e.g., Met. 1003a21)
    AKADEMIE = "akademie"               # Kant: work + volume + page
    AB_EDITION = "ab_edition"            # Kant KrV: A/B edition pages (e.g., A51/B75)
    PARAGRAPH = "paragraph"              # Hegel: section §, R (remark), A (addition)
    SZ_PAGINATION = "sz_pagination"      # Heidegger: SZ page numbers
    DIELS_KRANZ = "diels_kranz"          # Pre-Socratics: philosopher# + A/B/C + fragment#
    LINE_NUMBER = "line_number"          # Poetry, classical texts: work + line/verse
    CHAPTER_VERSE = "chapter_verse"      # Biblical: Book + chapter:verse
    LEGAL = "legal"                      # Legal: § paragraph, ¶, Bluebook pincites
    CUSTOM = "custom"                    # Project-specific system
```

### Pattern 4: Commentary Apparatus
**What:** Separate model for commentary that uses passage references (not markers)
**When to use:** Critical editions, Talmud-style multi-layer commentary, editorial commentary
**Why:** Commentary is fundamentally different from notes: organized by passage, not by markers. TEI has separate `<app>` model for this.

```python
# Informed by TEI critical apparatus (app/lem/rdg) and location-referenced method
class Commentary(GTElement):
    """Commentary organized by passage reference, not by markers."""
    element_type: Literal["commentary"] = "commentary"
    source: str = Field(description="Who wrote the commentary (e.g., 'Rashi', 'editor')")

    reference_system: ReferenceSystem = Field(description="How it locates the passage")
    target_location: LocationRef | None = Field(default=None, description="Where in GT the passage is")
    content: list[ContentSpan] = Field(description="Commentary content spans")
    layer: str | None = Field(default=None, description="Commentary layer identifier")
```

### Anti-Patterns to Avoid

- **Dual-representation relationships:** Do NOT keep both embedded references (Note.body_marker) AND separate relationship models (FootnoteLink). Pick one source of truth -- embedded references, with utility functions to construct graphs on demand.

- **Content-named spatial labels:** Spatial labels should describe visual appearance, not semantic content. BIBLIOGRAPHY_AREA is borderline: it IS visually distinctive (different formatting, indentation), so keeping it is acceptable. But naming should prioritize visual pattern.

- **Conflating independent dimensions:** CitationType's current 7 values mix format (how it appears) with reference system (what coordinates it uses). Always keep orthogonal axes in separate enums.

- **Breaking backward compatibility silently:** Bump SCHEMA_VERSION to 2.0.0. Existing v1.0.0 GT files will not validate against v2.0.0 schema. This is correct -- forced migration is better than silent incompatibility.

## Common Pitfalls

### Pitfall 1: Discriminated Union Breakage
**What goes wrong:** Changing element_type Literal values or adding/removing union members breaks JSON deserialization of existing data and all tests.
**Why it happens:** The discriminated union in `semantic.py` routes on `element_type`. Renaming "footnote" to "note" means existing JSON with `"element_type": "footnote"` fails validation.
**How to avoid:**
1. Update SemanticElement union definition AFTER all member models are updated
2. Update all test data dictionaries that use element_type values
3. Bump schema version to signal incompatibility
4. Update example JSON files simultaneously
**Warning signs:** ValidationError with "union_tag_invalid" in test output.

### Pitfall 2: Circular Import Risk
**What goes wrong:** LocationRef in base.py referenced by semantic.py, but semantic elements referenced by document.py which uses types from base.py.
**Why it happens:** Adding shared types (LocationRef) to base.py and using them across modules can create import cycles if not careful.
**How to avoid:** Keep LocationRef in base.py (it's a base type). It has no dependencies on other schema modules. Imports flow: base.py <- labels.py <- spatial.py <- page.py, and base.py <- labels.py <- semantic.py <- document.py. This DAG is already clean.
**Warning signs:** ImportError at module load time.

### Pitfall 3: Config Profile Drift
**What goes wrong:** Renaming/adding/removing enum values without updating all 4 YAML profile files causes validation warnings/errors when loading profiles.
**Why it happens:** Profile YAML files list label values by string. If enum values change, YAML must change too.
**How to avoid:** Update profiles in the same plan/wave as enum changes. Run profile loading tests immediately after.
**Warning signs:** "label 'X' not in profile" warnings in validation tests.

### Pitfall 4: Test Data Explosion
**What goes wrong:** 225 tests need updating. Attempting to update all at once leads to merge conflicts and lost context.
**Why it happens:** Every test that constructs a Footnote, Endnote, or uses old enum values needs changing.
**How to avoid:** Group test updates by model: first base model tests, then note tests, then citation tests, etc. Use find-and-replace for straightforward renames (Footnote -> Note), manual editing for structural changes.
**Warning signs:** Failing test count growing faster than fixing rate.

### Pitfall 5: Losing the ContentSpan.text Field
**What goes wrong:** CONTEXT.md says "ContentSpan references by location... rather than duplicating text." This could be interpreted as removing ContentSpan.text entirely.
**Why it happens:** The canonical text source is Region.text. ContentSpan should REFERENCE it, not duplicate it.
**How to avoid:** ContentSpan KEEPS its text field for convenience and self-containedness (GT files should be readable without cross-referencing). The "references by location" means it ALSO has char_offset/char_length for precise positioning. Both coexist.
**Warning signs:** Loss of human-readability in GT files if text is removed.

### Pitfall 6: Over-Abstracting ReferenceSystem
**What goes wrong:** Making ReferenceSystem too abstract (just CUSTOM for everything) loses the schema's documentation value.
**Why it happens:** Every canonical system is "custom" in some sense.
**How to avoid:** Include well-established systems as named enum values (Stephanus, Bekker, etc.). Use CUSTOM only for truly project-specific systems. The enum documents which systems the schema was designed to handle.
**Warning signs:** All real-world citations using CUSTOM because nothing else matches.

## Research Findings by Topic

### 1. TEI P5 Note Model (HIGH confidence)

TEI P5 uses a single `<note>` element for all note types, differentiated by attributes:
- `@place`: "bottom" (footnote), "end" (endnote), "margin" (marginal)
- `@resp`: Responsibility (links to `<respStmt>`)
- `@n`: Marker symbol/number
- `@anchored`: Whether anchor position is preserved
- `@type`: Classification (e.g., "gloss")

This directly validates the DECIDED Note consolidation. TEI has 30+ years of experience with this model.

**Source:** [TEI P5 note element](https://www.tei-c.org/release/doc/tei-p5-doc/en/html/ref-note.html)

### 2. TEI Critical Apparatus (HIGH confidence)

TEI models critical apparatus through `<app>` (apparatus entry), `<lem>` (lemma/base text), `<rdg>` (variant reading). Three linking methods:
1. **Location-referenced:** Uses canonical references (like Stephanus). Best for printed apparatus.
2. **Double end-point attachment:** Uses `from`/`to` with xml:id. Handles overlapping variants.
3. **Parallel segmentation:** All variants inline. Cannot handle overlapping variants.

For our Commentary model, the **location-referenced** method is most relevant: commentary locates passages by canonical coordinates (Stephanus, Bekker, etc.) -- exactly matching the DECIDED design.

**Source:** [TEI P5 Critical Apparatus](https://www.tei-c.org/release/doc/tei-p5-doc/en/html/TC.html)

### 3. TEI Standoff Annotation for Text Properties (MEDIUM confidence)

TEI addresses overlapping annotations through standoff markup:
- `<seg>` elements with `@xml:lang` for language at any granularity
- Standoff containers (`<standOff>`) separate annotation from primary data
- `att.fragmentable` for elements split across structural boundaries
- Multiple annotation layers can coexist without hierarchy conflicts

**Implication for Text Element Model:** A layered approach (formatting layer + language layer + semantic layer) is the established pattern. However, for GT annotation simplicity, a single TextSpan model that captures all properties at once may be more practical for human annotators, even if less theoretically pure.

**Recommendation:** Use a hybrid: single TextSpan for annotation, but structured so individual properties can be set independently (all Optional). This supports incremental annotation (annotator marks language first, formatting later) without requiring separate layer models.

**Source:** [TEI P5 Linking, Segmentation, and Alignment](https://tei-c.org/release/doc/tei-p5-doc/en/html/SA.html)

### 4. DocLayNet Label Taxonomy (HIGH confidence)

**DocLayNet v1 (11 classes):** Caption, Footnote, Formula, List-item, Page-footer, Page-header, Picture, Section-header, Table, Text, Title

**DocLayNet v2 (17 classes):** Added Document Index (=TOC), Code, Checkbox-Selected, Checkbox-Unselected, Form, Key-Value Region

**Key observations:**
- Single "Footnote" label (no endnote distinction) -- consistent with our consolidation
- "Document Index" = our TOC_AREA -- validates adding this label
- "Code" = our CODE_BLOCK -- validates adding this
- Single-label annotation (not multi-label)
- Non-overlapping rectangular boxes enforced at tooling level
- No ABSTRACT or SIDEBAR labels
- No BIBLIOGRAPHY distinction (would be labeled "Text" in DocLayNet)

**PubLayNet (5 classes):** Text, Title, List, Table, Figure. Much simpler.

**Mapping implications:** Our schema has MORE labels than DocLayNet. This is intentional -- we serve different downstream tasks (layout + semantic + citation extraction). We need a mapping layer, not label reduction.

**Sources:** [DocLayNet paper](https://ar5iv.labs.arxiv.org/html/2206.01062), [DocLayNet v2](https://arxiv.org/html/2509.11720v1), [DocLayNet GitHub](https://github.com/DS4SD/DocLayNet)

### 5. ALTO XML Text Properties (MEDIUM confidence)

ALTO 4.0 provides:
- Hierarchical: Page > PrintSpace > TextBlock > TextLine > String
- `LANG` attribute at String, TextLine, TextBlock levels with inheritance
- `TextStyle`: FONTWIDTH, FONTTYPE, FONTSTYLE, FONTFAMILY, FONTCOLOR, FONTSIZE
- `ParagraphStyle`: alignment, indentation, line spacing
- Style references via STYLEREFS attribute
- No cross-page mechanisms

**Implication:** ALTO's language inheritance model (set at block, override at line/word) is practical. Our schema should support a default document language with override at the span level.

**Source:** [ALTO Schema](https://github.com/altoxml/schema), [ALTO documentation](https://github.com/altoxml/documentation/wiki/Structure-of-ALTO-files)

### 6. PAGE XML Region Model (MEDIUM confidence)

PAGE XML 2019 provides:
- Page > Region > TextLine > Word > Glyph hierarchy
- Nested regions (sub-regions allowed)
- TextEquiv for text content at each level
- TextStyle per region (font properties)
- Reading order via ordered groups
- No cross-page linking

**Implication:** PAGE XML supports nested regions -- relevant to our RESEARCH item about sub-regions for TABLE cells. However, PAGE XML's nesting is for the full hierarchy, while we only need optional children.

**Source:** [PAGE XML GitHub](https://github.com/PRImA-Research-Lab/PAGE-XML)

This covers all major academic citation systems. Use CUSTOM for truly project-specific systems. The enum is educational -- it documents what the schema was designed to handle.

### 8. Chicago Manual Citation Classification (HIGH confidence)

Chicago Manual of Style (now 18th edition, 17th still widely used) defines two systems:
1. **Notes-Bibliography (NB):** Footnotes/endnotes contain the citation. Bibliography at end.
2. **Author-Date (AD):** Parenthetical in-text citations. Reference list at end.

The NB system is where "footnote IS the citation" -- exactly the Chicago Footnote-as-Citation DECIDED pattern. In our model: a Note element's content region is also referenced by a Citation element's location. They coexist spatially.

**Source:** [Chicago Manual](https://www.chicagomanualofstyle.org/tools_citationguide.html), [Purdue OWL](https://owl.purdue.edu/owl/research_and_citation/chicago_manual_17th_edition/cmos_formatting_and_style_guide/chicago_manual_of_style_17th_edition.html)

### 9. BCP 47 Language Tags (HIGH confidence)

Structure: `language[-script[-region]]`
- Primary language: 2-letter ISO 639-1 (en, de, el, la, fr) or 3-letter ISO 639-3
- Script subtag: 4 letters, first capitalized (Latn, Grek, Hebr, Arab)
- Region subtag: 2-letter ISO 3166-1 or 3-digit UN M49

Common tags for scholarly texts:
- `de` -- German
- `el` or `el-Grek` -- Greek (modern, Greek script)
- `grc` -- Ancient Greek
- `la` -- Latin
- `fr` -- French
- `he` or `he-Hebr` -- Hebrew
- `ar` or `ar-Arab` -- Arabic

**Recommendation:** Use BCP 47 as-is (string field, not enum). Document the format and provide common examples. Don't validate tag format at model level -- it's a string following a convention. Validation can be a profile-level check if needed.

**Source:** [W3C Language Tags](https://www.w3.org/International/articles/language-tags/), [BCP 47 Wikipedia](https://en.wikipedia.org/wiki/IETF_language_tag)

### 10. Pydantic Discriminated Union Extensibility (HIGH confidence)

Pydantic v2 supports:
- **String discriminator:** `Field(discriminator='element_type')` -- current approach, works well
- **Custom discriminator functions:** Can handle unknown types gracefully
- **Nested discriminators:** Multiple discriminator levels
- **Tag-based routing:** `Annotated[type, Tag('name')]` for non-field discriminators

For extensibility (tension #3 in CONTEXT.md), the current approach works:
1. `GTElement` has `extra="allow"` -- unknown fields preserved
2. `GTProfile` uses `set[str]` -- custom labels beyond enum accepted
3. For custom semantic elements: users can use `extra="allow"` fields on DocumentGT directly

A true plugin system (registering new element types into the union) is unnecessary for Phase 1.1. The existing `extra="allow"` pattern handles forward compatibility. If a project needs a custom element type, they can: (a) use tags on a standard element, or (b) store custom elements in DocumentGT's extra fields.

**Source:** [Pydantic Unions docs](https://docs.pydantic.dev/latest/concepts/unions/)

### 11. Multi-Label vs Single-Label for Spatial Labels (MEDIUM confidence)

Current research (DocHieNet, 2024 EMNLP) explores hierarchical document structure, but standard layout detection datasets (DocLayNet, PubLayNet) use **single-label** annotation for spatial regions. Our schema already supports multi-label via `Region.semantic_labels: list[SemanticType]`, but spatial label (`Region.label`) is single-value.

**Recommendation:** Keep single-label for spatial label (consistent with industry standard). The semantic_labels list provides the multi-dimensional annotation needed. If a region truly serves multiple spatial purposes (rare), use the primary visual role as the label and document the secondary role in tags or semantic_labels.

**Source:** [DocLayNet paper](https://ar5iv.labs.arxiv.org/html/2206.01062), [DocHieNet](https://aclanthology.org/2024.emnlp-main.65.pdf)

### 12. Note Spatial Label Decision (MEDIUM confidence)

DECIDED: Research whether to use unified NOTE_AREA vs visually-named variants.

**DocLayNet uses:** Single "Footnote" label. No endnote distinction. No continuation label.

**Current schema has:** FOOTNOTE_AREA, ENDNOTE_AREA, FOOTNOTE_CONTINUATION (3 labels)

**Options:**
1. `NOTE_AREA` + `NOTE_CONTINUATION` (2 labels, consistent with semantic consolidation)
2. Keep FOOTNOTE_AREA + ENDNOTE_AREA (visually distinct: bottom-of-page vs end-of-chapter)
3. Use visual names: `PAGE_BOTTOM_NOTES` + `NOTE_SECTION` + `NOTE_CONTINUATION`

**Recommendation:** Use `NOTE_AREA` + `NOTE_CONTINUATION` (option 1). Rationale:
- Consistent with semantic Note consolidation
- Layout detection models don't need to distinguish footnote areas from endnote areas -- both are text blocks with special formatting
- The semantic distinction (footnote vs endnote) lives in the Note model's `placement` field
- Reduces enum size
- For external model interop, the adapter maps DocLayNet "Footnote" -> our "note_area"

## Open Questions

1. **Sub-region model scope**
   - What we know: TABLE needs cells, FIGURE needs sub-figures. PAGE XML supports nested regions.
   - What's unclear: How deep should nesting go? Is `children: list[Region]` sufficient, or does it need its own model?
   - Recommendation: Add optional `children: list[Region]` on Region. Keep it simple -- one level of nesting. Validate that children bboxes are within parent bbox. Defer complex multi-level nesting to Phase 4 annotation tool.

2. **SousRature in Text Element Model**
   - What we know: SousRature is semantically distinct from strikethrough formatting. It's philosophically meaningful, not editorial.
   - What's unclear: Should SousRature remain a standalone SemanticElement, or should it become a semantic_role on a TextSpan?
   - Recommendation: Keep SousRature as a standalone SemanticElement. It has its own verification lifecycle and is a document-level semantic annotation, not a text property. A TextSpan's `semantic_role` could be "sous_rature" for the text property view, while the SousRature SemanticElement provides the cross-document annotation with full metadata.

3. **Text Element Model implementation depth**
   - What we know: Mixed-language text needs span-level annotation. Multiple annotation dimensions exist (formatting, language, semantic).
   - What's unclear: How much of the text element model to implement in Phase 1.1 vs defer.
   - Recommendation: In Phase 1.1, add language support to FormattingAnnotation (add `language: str | None` field) and document the TextSpan concept in the schema guide. Full TextSpan implementation can be Phase 2 when extractors need it. Rationale: The text element model is RESEARCH status, and Phase 1.1 already has extensive DECIDED changes to implement.

4. **BibliographicRecord scope**
   - What we know: ParsedCitation is too limited (only author, year, page_ref, work). BibEntry needs title, journal, volume, DOI, etc.
   - What's unclear: Exactly which fields are needed and whether to use CSL-JSON field names for interop.
   - Recommendation: Create BibliographicRecord with common scholarly fields (title, authors, year, journal, volume, issue, pages, doi, isbn, publisher, edition, url). Don't attempt CSL-JSON compatibility -- that's a Phase 2 extractor concern. Keep it pragmatic.

5. **SemanticElement extensibility mechanism**
   - What we know: Current union is closed. `extra="allow"` on GTElement handles unknown fields but not unknown types.
   - What's unclear: Whether to use custom discriminator function that gracefully handles unknown element_types.
   - Recommendation: For Phase 1.1, keep the typed union. Unknown element types should raise validation errors -- they indicate schema version mismatch, not extensibility use. Document in schema guide how to propose new element types. True extensibility (plugin registration) is overengineering for now.
