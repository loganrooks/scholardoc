## Summary

Phase 1.1 is a schema redesign phase that restructures the ScholarGT label taxonomy. The original scope (Note consolidation, Commentary apparatus, CitationType decomposition, ScanQuality replacement, cross-page relationships, self-describing pages) is now augmented with six Structural Fix Proposals adopted from the non-conservative gap analysis v2.

The SFP additions introduce: (1) a LayoutRegister model for multi-register document layouts affecting 57% of the corpus, (2) explicit text direction on Region and PageGT for the 33% RTL corpus, (3) a ScriptVariant enum for Rashi-vs-square Hebrew distinction across ~1,300 pages, (4) COLOR in FormattingType with color_value/color_semantic for Koren Talmud's ~449 pages, (5) INDEX_AREA spatial label for standard scholarly apparatus, and (6) CATCHWORD reference system for dibbur ha-matchil anchoring across ~1,300 pages. SFP-7 (content_layer for handwritten annotations) is deferred -- only 4 pages affected.

External research validates the SFP designs. ALTO 4.0 provides FONTCOLOR as hexBinary in TextStyle, confirming color annotation is standard in document GT. hOCR uses HTML `dir` attribute for text directionality and supports writing direction metadata per element. PAGE XML uses ReadingOrder groups to model column/register flow, though no standard provides a first-class "register" concept -- our LayoutRegister model fills a genuine gap. Sefaria's Commentary Matcher (Dibur Hamatchil Matcher) confirms that catchword anchoring is the primary computational reference mechanism for Talmudic commentary. Unicode does NOT distinguish Rashi script from square Hebrew (both are U+0590-U+05FF, "he-Hebr") -- the distinction is purely typographic, confirming the need for ScriptVariant at the annotation level.

**Primary recommendation:** Revise existing Phase 1.1 plans (0/5 executed) to absorb SFP-1 through SFP-6 as enumerated in the Plan Impact section. No new plans needed; the additions are field-level and enum-level changes (~41 lines of model code) that fit into the existing 5-plan structure.

### Pattern 1: LocationRef for Consistent Cross-Element Referencing
**What:** Standardized model for referencing a position in the GT corpus
**When to use:** Any semantic element that references a page+region+character position
**Why:** Currently, `page`, `region_id`, `char_offset`, `char_length` are scattered across models inconsistently. LocationRef provides a single reusable type.

```python
# Source: Design decision from CONTEXT.md tension #4
class LocationRef(BaseModel):
    """Reference to a specific location in the GT corpus."""
    page: int = Field(description="0-based page index")
    region_id: str = Field(description="Region ID on the page")
    char_offset: int | None = Field(default=None, description="Character offset within region text")
    char_length: int | None = Field(default=None, description="Length of referenced text span")
```

### Pattern 2: LayoutRegister for Multi-Register Documents [NEW -- SFP-1]
**What:** A named reading stream or column identity with metadata, referenced by regions
**When to use:** Documents with parallel text streams (dual columns, multi-layer commentary, bilingual)
**Why:** 57% of corpus uses multi-register layouts. No standard (ALTO, PAGE XML, hOCR) provides a first-class register concept. ALTO uses ComposedBlock for hierarchical grouping and IDNEXT for reading sequence, but neither names registers or carries register-level metadata. PAGE XML uses ReadingOrder groups but lacks register identity. Our LayoutRegister fills a genuine gap in GT annotation standards.

```python
# Source: SFP-1 from gap analysis v2
# Validated: No competing standard provides this; ALTO ComposedBlock is closest but lacks metadata
class LayoutRegister(BaseModel):
    """A named reading stream or column in a multi-register document.

    Provides first-class identity for parallel text streams, commentary
    layers, bilingual columns, and multi-register layouts. Each register
    maps to a set of regions across pages.
    """
    register_id: str = Field(description="Unique register identifier (e.g., 'hegel', 'genet', 'rashi')")
    name: str = Field(description="Human-readable register name")
    author: str | None = Field(default=None, description="Author or attributed source")
    language: str | None = Field(default=None, description="Primary BCP 47 language tag")
    text_direction: Literal["ltr", "rtl"] | None = Field(
        default=None, description="Base text direction for this register"
    )
    position_convention: str | None = Field(
        default=None,
        description="Layout convention (e.g., 'left_column', 'upper_register', 'inner_margin', 'central')"
    )
    typeface_convention: str | None = Field(
        default=None, description="Expected typeface family (e.g., 'rashi_script', 'square_hebrew', 'serif_9pt')"
    )
```

On Region, add:
```python
    register_id: str | None = Field(
        default=None, description="LayoutRegister this region belongs to"
    )
```

On DocumentGT, add:
```python
    registers: list[LayoutRegister] = Field(
        default_factory=list, description="Named reading streams / column identities in this document"
    )
```

### Pattern 3: Explicit Text Direction [NEW -- SFP-2]
**What:** Explicit text direction at Region and Page level
**When to use:** Every region and page, especially for RTL corpus (33%)
**Why:** ALTO 4.0 lacks a WRITING_DIR attribute (only has ROTATION for visual rotation). hOCR uses HTML `dir` attribute (ltr/rtl). TEI recommends deriving direction from `@xml:lang` for most cases but acknowledges that mixed-direction text (common in Talmudic texts with Hebrew + embedded numbers/Latin) requires explicit direction. For ground truth annotation, direction must be ANNOTATED, not derived -- derivation introduces error and burdens consumers.

```python
# On Region (spatial.py):
    text_direction: Literal["ltr", "rtl", "bidi"] | None = Field(
        default=None, description="Base text direction for this region's content"
    )

# On PageGT (page.py):
    base_direction: Literal["ltr", "rtl"] | None = Field(
        default=None, description="Default text direction for this page (most regions inherit this)"
    )
```

**Design note:** Region uses "bidi" for regions containing mixed-direction text where neither LTR nor RTL is dominant. PageGT uses only "ltr"/"rtl" (no "bidi") because page-level base direction is always one or the other.

### Pattern 4: ScriptVariant Enum [NEW -- SFP-3]
**What:** Enum for script variants within a writing system where BCP 47 is insufficient
**When to use:** Rashi script vs square Hebrew distinction (~1,300 pages)
**Why:** Unicode encodes both Rashi script and square Hebrew using the same codepoints (U+0590-U+05FF). BCP 47 classifies both as "he-Hebr". The distinction is purely typographic: Rashi script uses flowing semi-cursive letterforms; square Hebrew uses rigid geometric block forms. This typographic distinction IS the semantic signal in Talmudic texts -- it identifies commentary vs base text. Specialized OCR models exist specifically for Rashi script (CNN+LSTM architectures), confirming that the visual distinction is computationally real.

```python
# Source: SFP-3 from gap analysis v2
# Validated: Unicode U+0590-U+05FF is shared; BCP 47 "he-Hebr" covers both
# Confirmed: Rashi script OCR research (arXiv:1811.01290) treats as distinct classification target
class ScriptVariant(str, Enum):
    """Script variant within a writing system, for cases where
    BCP 47 script subtags are insufficient.

    Primary use: distinguishing Rashi script from square (block) Hebrew,
    which both fall under BCP 47 'Hebr' but carry distinct semantic meaning
    in Talmudic typography.
    """
    SQUARE_HEBREW = "square_hebrew"       # Standard block Hebrew (Gemara, biblical text)
    RASHI_SCRIPT = "rashi_script"         # Rashi/semi-cursive (commentary tradition)
    NASTALIQ = "nastaliq"                 # Persian/Urdu calligraphic variant (future)
    NASKH = "naskh"                       # Standard Arabic print (future)
    FRAKTUR = "fraktur"                   # German blackletter (historical texts)
    CUSTOM = "custom"                     # Project-specific variant
```

On FormattingAnnotation, add:
```python
    script_variant: ScriptVariant | None = Field(
        default=None,
        description="Script variant for this span (when BCP 47 script subtag is insufficient)"
    )
```

### Pattern 5: Color Annotation [NEW -- SFP-4]
**What:** COLOR formatting type with structured color value and semantic meaning
**When to use:** Koren Talmud (~449 pages) and any text using color as semantic signal
**Why:** ALTO 4.0 has FONTCOLOR as hexBinary in TextStyle -- confirming color annotation is standard in document GT schemas. Our current FormattingType lacks COLOR entirely. The Koren Talmud uses color to distinguish Gemara text, Mishnah text, commentary layers, and translation emphasis. This is structured semantic information, not decorative color.

```python
# Add to FormattingType enum:
    COLOR = "color"   # Text rendered in a specific color (semantic signal)

# Add to FormattingAnnotation:
    color_value: str | None = Field(
        default=None,
        description="CSS color value when formatting_type is COLOR (e.g., '#FF0000', 'red')"
    )
    color_semantic: str | None = Field(
        default=None,
        description="Semantic meaning of the color (e.g., 'gemara_text', 'mishnah_text')"
    )
```

**Design note:** color_value uses CSS color format (hex or named) rather than ALTO's hexBinary, since CSS colors are more widely understood and the Pydantic models serialize to JSON, not XML.

### Pattern 6: Note Model with Dual Markers (unchanged from v1 research)
**What:** Consolidated Note replacing Footnote/Endnote with explicit body and content marker locations
**When to use:** Any note-like element regardless of placement
**Why:** TEI P5 uses single `<note>` with `@place`. Differences are properties, not types.

```python
# Informed by TEI P5 <note> element: @place=bottom|end, @resp, @n
class Note(GTElement):
    """A scholarly note (footnote, endnote, marginal note) with marker locations."""
    element_type: Literal["note"] = "note"
    body_marker: LocationRef = Field(description="Where reference marker appears in body text")
    content_marker: LocationRef | None = Field(
        default=None, description="Where note content begins (important for endnotes)"
    )
    content: list[ContentSpan] = Field(description="Content spans (may cross pages)")
    placement: Literal["page_bottom", "end_of_chapter", "end_of_book", "margin"]
    scope: Literal["page", "chapter", "section", "essay", "document"] | None = Field(default=None)
    note_source: Literal["author", "translator", "editor"] | None = Field(default=None)
```

### Pattern 7: Orthogonal Citation Axes (augmented with CATCHWORD)
**What:** CitationFormat (how it looks) x ReferenceSystem (what coordinates it uses) x citation style (document-level)
**When to use:** Citation elements and MarginalReference elements share ReferenceSystem
**Why:** Current CitationType conflates format and reference system.

```python
class CitationFormat(str, Enum):
    PARENTHETICAL = "parenthetical"     # (Smith, 2020)
    NUMERIC = "numeric"                  # [1] or superscript
    INLINE_AUTHOR = "inline_author"      # Smith argues...
    NOTE_BASED = "note_based"            # Chicago NB: footnote IS citation
    AUTHOR_TITLE = "author_title"        # Author, Short Title

class ReferenceSystem(str, Enum):
    STANDARD = "standard"                # Author + Year + Page
    STEPHANUS = "stephanus"              # Plato: dialogue + page + section
    BEKKER = "bekker"                    # Aristotle: page + column + line
    AKADEMIE = "akademie"               # Kant: work + volume + page
    AB_EDITION = "ab_edition"            # Kant KrV: A/B edition pages
    PARAGRAPH = "paragraph"              # Hegel: section paragraph, remark, addition
    SZ_PAGINATION = "sz_pagination"      # Heidegger: SZ page numbers
    DIELS_KRANZ = "diels_kranz"          # Pre-Socratics: philosopher + fragment
    LINE_NUMBER = "line_number"          # Poetry, classical texts
    CHAPTER_VERSE = "chapter_verse"      # Biblical: Book + chapter:verse
    LEGAL = "legal"                      # Legal citations
    CATCHWORD = "catchword"              # [NEW SFP-6] Dibbur ha-matchil: commentary anchored by verbatim text quotation
    CUSTOM = "custom"                    # Project-specific system
```

### Pattern 8: Commentary Apparatus (unchanged from v1 research)
**What:** Separate model for commentary using passage references (not markers)
**When to use:** Critical editions, Talmud-style multi-layer commentary
**Why:** Commentary is fundamentally different from notes. TEI has separate `<app>` model.

```python
class Commentary(GTElement):
    """Commentary organized by passage reference, not by markers."""
    element_type: Literal["commentary"] = "commentary"
    source: str = Field(description="Who wrote the commentary (e.g., 'Rashi', 'editor')")
    passage_ref: str = Field(description="What passage it comments on (canonical coordinates)")
    reference_system: ReferenceSystem = Field(description="How it locates the passage")
    target_location: LocationRef | None = Field(default=None)
    content: list[ContentSpan] = Field(description="Commentary content spans")
    layer: str | None = Field(default=None, description="Commentary layer identifier")
```

### Anti-Patterns to Avoid

- **Dual-representation relationships:** Do NOT keep both embedded references (Note.body_marker) AND separate relationship models (FootnoteLink). Pick one source of truth.

- **Content-named spatial labels:** Spatial labels should describe visual appearance, not semantic content. BIBLIOGRAPHY_AREA is borderline but acceptable (visually distinctive).

- **Conflating independent dimensions:** CitationType's current 7 values mix format with reference system. Always keep orthogonal axes in separate enums.

- **Using UNKNOWN for known entities:** INDEX_AREA is a well-understood scholarly apparatus element. Using UNKNOWN + tags for it is semantically wrong. Use specific labels.

- **Using CUSTOM for primary mechanisms:** CATCHWORD (dibbur ha-matchil) appears on ~1,300 pages. Using CUSTOM for the single most common reference system in Hebrew texts is a taxonomy error. Name it.

- **Deriving what should be annotated:** Text direction should be EXPLICIT in ground truth, not derived from language tags. Derivation introduces error and burdens every consumer.

## Common Pitfalls

### Pitfall 1: Discriminated Union Breakage
**What goes wrong:** Changing element_type Literal values or adding/removing union members breaks JSON deserialization of existing data and all tests.
**Why it happens:** The discriminated union in `semantic.py` routes on `element_type`. Renaming "footnote" to "note" means existing JSON with `"element_type": "footnote"` fails validation.
**How to avoid:**
1. Update SemanticElement union definition AFTER all member models are updated
2. Update all test data dictionaries that use element_type values
3. Bump schema version to signal incompatibility
4. Update example JSON files simultaneously
**Warning signs:** ValidationError with "union_tag_invalid" in test output.

### Pitfall 2: Circular Import Risk
**What goes wrong:** LocationRef in base.py referenced by semantic.py, but semantic elements referenced by document.py which uses types from base.py.
**Why it happens:** Adding shared types (LocationRef) to base.py and using them across modules can create import cycles if not careful.
**How to avoid:** Keep LocationRef in base.py (it's a base type). It has no dependencies on other schema modules. Imports flow: base.py <- labels.py <- spatial.py <- page.py, and base.py <- labels.py <- semantic.py <- document.py. This DAG is already clean. LayoutRegister can be in document.py (alongside DocumentGT) or a new registers.py; either maintains the DAG.
**Warning signs:** ImportError at module load time.

### Pitfall 3: Config Profile Drift
**What goes wrong:** Renaming/adding/removing enum values without updating all 4 YAML profile files causes validation warnings/errors when loading profiles.
**Why it happens:** Profile YAML files list label values by string. If enum values change, YAML must change too.
**How to avoid:** Update profiles in the same plan/wave as enum changes. Run profile loading tests immediately after. SFP additions (ScriptVariant, COLOR, INDEX_AREA, CATCHWORD) all need profile entries.
**Warning signs:** "label 'X' not in profile" warnings in validation tests.

### Pitfall 4: Test Data Explosion
**What goes wrong:** 225 tests need updating. Attempting to update all at once leads to merge conflicts and lost context.
**Why it happens:** Every test that constructs a Footnote, Endnote, or uses old enum values needs changing.
**How to avoid:** Group test updates by model: first base model tests, then note tests, then citation tests, etc. Use find-and-replace for straightforward renames (Footnote -> Note), manual editing for structural changes. SFP additions need NEW tests but don't break existing tests (they're additive).
**Warning signs:** Failing test count growing faster than fixing rate.

### Pitfall 5: Register Validation Complexity
**What goes wrong:** LayoutRegister model introduces cross-referencing between Region.register_id and DocumentGT.registers that can have dangling references.
**Why it happens:** Registers are document-level; regions are page-level. The linkage crosses the PageGT/DocumentGT boundary.
**How to avoid:** Region.register_id is a simple string (no FK enforcement at model level). Add a DocumentGT model_validator that warns on register_id references not in registers list. Symmetric to existing reading_order validation on PageGT. Do NOT enforce at Region construction time -- regions may be annotated before registers are defined.
**Warning signs:** Overly strict validation that prevents incremental annotation.

### Pitfall 6: Color Annotation Ambiguity
**What goes wrong:** FormattingAnnotation with formatting_type=COLOR but no color_value, or color_value set when formatting_type != COLOR.
**Why it happens:** color_value and color_semantic are only meaningful when formatting_type is COLOR.
**How to avoid:** Add a model_validator on FormattingAnnotation that: (a) warns if formatting_type is COLOR but color_value is None, (b) warns if color_value is set but formatting_type is not COLOR. Use warnings, not errors -- annotation may be incremental.
**Warning signs:** Confusing GT data where COLOR annotations lack actual color information.

### Pitfall 7: Losing the ContentSpan.text Field
**What goes wrong:** CONTEXT.md says "ContentSpan references by location... rather than duplicating text." This could be interpreted as removing ContentSpan.text entirely.
**Why it happens:** The canonical text source is Region.text. ContentSpan should REFERENCE it, not duplicate it.
**How to avoid:** ContentSpan KEEPS its text field for convenience and self-containedness. The "references by location" means it ALSO has char_offset/char_length for precise positioning. Both coexist.
**Warning signs:** Loss of human-readability in GT files if text is removed.

## Research Findings by Topic

### SFP-1: Layout Registers -- How Standards Handle Multi-Column (HIGH confidence)

**ALTO 4.0:**
- Uses ComposedBlock (a block containing other blocks) for hierarchical grouping
- Uses IDNEXT attribute on blocks for reading sequence pointers
- No concept of named registers, column identity, or register-level metadata
- ComposedBlock is purely structural grouping; no author, language, or direction metadata
- Source: [ALTO 4.0 XSD](https://github.com/altoxml/schema/blob/master/v4/alto-4-0.xsd)

**PAGE XML 2019:**
- Uses ReadingOrder with OrderedGroup and RegionRefIndexed for sequencing
- TextRegion has a `type` attribute (heading, paragraph, etc.) but no column/register identity
- Nested regions supported (sub-regions within regions)
- No concept of named reading streams or register metadata
- Source: [PAGE XML GitHub](https://github.com/PRImA-Research-Lab/PAGE-XML)

**hOCR:**
- Uses HTML `class` attributes for semantic roles (ocr_carea for content areas)
- Content areas derive from "a linear stream of textual content, which flows into the areas"
- Supports multiple body texts in newspaper layouts, but no named register concept
- Source: [hOCR spec](http://kba.github.io/hocr-spec/1.2/)

**TEI P5:**
- Critical apparatus uses `<app>`/`<lem>`/`<rdg>` for textual variants with `@wit` for witness attribution
- Parallel segmentation method displays versions in columns with `@type` attributes
- `<cb>` element marks column breaks; columns are presentational, not semantic entities
- No "register" concept; commentary is modeled via `<note>` with `@type="commentary"`
- Source: [TEI P5 Critical Apparatus](https://www.tei-c.org/release/doc/tei-p5-doc/en/html/TC.html)

**Conclusion:** No existing standard provides a first-class "register" or "reading stream" concept. All standards handle multi-column layouts through spatial grouping (ComposedBlock, ReadingOrder groups) or presentational breaks (`<cb>`), but none associate metadata (author, language, direction, typeface) with a named column identity. **Our LayoutRegister model is genuinely novel for GT annotation.** This is appropriate -- the multi-register scholarly text (Talmud, Derrida dual-column, bilingual editions) is underserved by existing standards.

### SFP-2: Text Direction -- How Standards Handle RTL (HIGH confidence)

**TEI P5:**
- TEI Text Directionality Draft (2014) proposed `@dir` attribute with values "ltr", "rtl", "auto"
- Current TEI P5 relies on `@xml:lang` to imply direction via Unicode Bidi Algorithm
- Explicit direction encoding is "not normally needed" per TEI guidelines, BUT this is for text display, not ground truth annotation
- For mixed-direction text, TEI recommends Unicode bidi embedding characters (LRE, RLE) -- but W3C advises against these in XML
- Source: [TEI Text Directionality Draft](https://wiki.tei-c.org/index.php/Text_Directionality_Draft)

**ALTO 4.0:**
- Has `ROTATION` attribute on blocks (degrees counterclockwise) for visual rotation
- **Does NOT have a WRITING_DIR or text direction attribute**
- Language (LANG) attribute is present; direction must be derived
- Source: [ALTO 4.0 XSD](https://github.com/altoxml/schema/blob/master/v4/alto-4-0.xsd)

**hOCR:**
- Uses HTML `dir` attribute (standard HTML attribute: "ltr", "rtl", "auto")
- Writing directions other than LTR are handled by conceptual rotation of bounding boxes
- Source: [hOCR spec](http://kba.github.io/hocr-spec/1.2/)

**W3C HTML/XML:**
- `dir` attribute on any element: "ltr", "rtl", "auto"
- Structural markup (block-level dir) recommended over Unicode bidi characters
- Source: [W3C Structural markup and RTL](https://www.w3.org/International/questions/qa-html-dir)

**Conclusion:** hOCR and HTML provide the closest model with the `dir` attribute. ALTO lacks explicit direction. TEI relies on language-implied direction. For ground truth annotation, explicit direction is essential because: (a) derivation from language is consumer burden, (b) bidi regions have no single direction derivable from language, (c) evaluation requires annotated truth, not derived truth. Our `text_direction: Literal["ltr", "rtl", "bidi"]` on Region and `base_direction: Literal["ltr", "rtl"]` on PageGT follows the hOCR/HTML pattern.

### SFP-3: Script Variant -- Rashi vs Square Hebrew (HIGH confidence)

**Unicode:**
- Both Rashi script and square Hebrew use the same Unicode block: U+0590-U+05FF (Hebrew)
- No separate codepoints or Unicode properties distinguish them
- Font-level distinction only: Rashi script requires specialized fonts (Noto Rashi Hebrew, 2018)
- OpenType features (dlig, ccmp) simulate cursive connections specific to Rashi
- Source: [Unicode Hebrew block](https://www.unicode.org/charts/PDF/U0590.pdf), [Rashi script Wikipedia](https://en.wikipedia.org/wiki/Rashi_script)

**BCP 47:**
- Both classified as "he-Hebr" (Hebrew language, Hebrew script)
- No variant subtag exists for Rashi script
- The distinction is sub-script-system (typographic variant), not a separate script
- Source: [IETF language tags](https://en.wikipedia.org/wiki/IETF_language_tag)

**OCR research:**
- Dedicated OCR models exist for Rashi script: CNN+LSTM architecture (arXiv:1811.01290)
- Book-specific CNN training needed due to typeface variation across publishers
- Tesseract community contribution for Hebrew Rashi script (tessdata_contrib)
- DICTA (Israel Center for Text Analysis) has Hebrew NLP tools but no published Rashi-specific font classifier
- Source: [Auto-ML for Rashi OCR](https://arxiv.org/abs/1811.01290), [Tesseract Rashi support](https://github.com/tesseract-ocr/tessdata_contrib/pull/6)

**Typographic role:**
- In Vilna Shas: square Hebrew = Gemara (base text), Rashi script = all commentaries
- In Mikraot Gedolot: square Hebrew = biblical text, Rashi script = commentaries
- The script variant IS the visual classifier for content role
- Some commentators (Ibn Ezra, Ramban) use square script even though they are commentators -- script variant != author identity
- Source: [Rashi script details](https://grokipedia.com/page/Rashi_script)

**Conclusion:** ScriptVariant enum is necessary and cannot be replaced by language tags, Unicode analysis, or author attribution. The enum should include SQUARE_HEBREW, RASHI_SCRIPT for the primary use case, with FRAKTUR (German blackletter), NASTALIQ/NASKH (Arabic variants) for future extensibility.

### SFP-4: Color Annotation (MEDIUM confidence)

**ALTO 4.0:**
- Has FONTCOLOR as `xsd:hexBinary` in TextStyleType (formattingAttributeGroup)
- Purely representational: records the color value, no semantic mapping
- Source: [ALTO 4.0 XSD](https://github.com/altoxml/schema/blob/master/v4/alto-4-0.xsd)

**PAGE XML:**
- TextStyle element supports font color attributes
- No semantic color mapping

**DocLayNet / PubLayNet:**
- Use color in visualization (color-coded labels in annotations)
- No color annotation IN the ground truth -- color is a rendering choice, not an annotation target

**Koren Talmud specifics (from gap analysis v2):**
- Color encodes Gemara text, Mishnah text, commentary attribution, translation emphasis
- Color is a structured semantic signal, not decorative
- ~449 pages (9% of corpus) use color meaningfully

**Conclusion:** ALTO validates that color annotation exists in GT standards. Our approach extends beyond ALTO by adding color_semantic (what the color MEANS), not just color_value (what the color IS). This is appropriate for ground truth where the semantic role of color matters for evaluation.

### SFP-5: INDEX_AREA (HIGH confidence)

**DocLayNet v2 (2024):**
- Added "Document Index" as a label in its v2 expansion (17 classes total)
- DocLayNet calls it "Document Index" -- referring to Table of Contents, not back-of-book index
- Source: [DocLayNet v2](https://arxiv.org/html/2509.11720v1)

**No standard explicitly names "back-of-book index":**
- DocLayNet's "Document Index" = our TOC_AREA (front-matter navigation)
- PubLayNet has no index label at all
- ALTO and PAGE XML have no dedicated index region type

**But indexes are visually distinctive:**
- Alphabetical entries with page references
- Dense two-column layout (typically)
- Indentation patterns for sub-entries
- Clearly distinct from regular TEXT_BLOCK

**Conclusion:** INDEX_AREA fills a gap that standards haven't addressed because most GT datasets focus on scientific articles (which rarely have indexes). Scholarly monographs (our corpus) consistently have them. Adding INDEX_AREA is consistent with having TOC_AREA and BIBLIOGRAPHY_AREA for other standard scholarly apparatus.

### SFP-6: CATCHWORD Reference System (HIGH confidence)

**Sefaria's Commentary Matcher (Dibur Hamatchil Matcher):**
- Sefaria developed automated matching: "looks at the dibur hamatchil and tries to place the comment in the right place"
- Cannot always match automatically: "sometimes the text appears multiple times in a daf, or might not match if there are abbreviations or textual variations"
- Manual verification required for ambiguous cases
- The mechanism is central enough to justify a dedicated matching tool
- Source: [Sefaria Wiki - Commentary Matcher](https://github.com/Sefaria/Sefaria-Project/wiki/Commentary-Matcher-(aka-Dibur-Hamatchil-Matcher))

**How catchword anchoring works:**
1. Commentary entry begins with verbatim quotation of source text (the "dibbur ha-matchil")
2. This opening quotation serves as the anchor -- it locates which passage the commentary addresses
3. The match is text-based: find the quoted words in the base text
4. Multiple matches possible (same phrase appears twice on a page) -- requires context resolution

**Why it deserves a named enum value:**
- Primary reference mechanism for ~1,300 pages of Hebrew/Aramaic corpus
- Computationally distinct: requires text matching, not coordinate lookup
- Sefaria built a dedicated tool for it (Commentary Matcher)
- Every Rashi and Tosafot entry on every page of Vilna Shas uses this mechanism
- The ReferenceSystem enum already includes DIELS_KRANZ and LEGAL (0 corpus pages each)

**Conclusion:** CATCHWORD in ReferenceSystem is a straightforward taxonomy correction. The mechanism is well-documented, computationally real (Sefaria built tools for it), and affects 25% of the corpus.

## Open Questions

1. **LayoutRegister placement: document.py or new file?**
   - What we know: LayoutRegister is referenced by DocumentGT.registers and Region.register_id
   - Options: Put in document.py (alongside DocumentGT), or create registers.py
   - Recommendation: Put in document.py. It's a small model (~10 lines), tightly coupled to DocumentGT. No circular import risk since Region only stores a string register_id.

2. **Sub-region model scope**
   - What we know: TABLE needs cells, FIGURE needs sub-figures. PAGE XML supports nested regions.
   - What's unclear: How deep should nesting go?
   - Recommendation: Add optional `children: list[Region]` on Region. Keep it simple -- one level of nesting. Validate that children bboxes are within parent bbox.

3. **SousRature in Text Element Model**
   - What we know: SousRature is semantically distinct from strikethrough formatting.
   - Recommendation: Keep SousRature as a standalone SemanticElement. It has its own verification lifecycle.

4. **Text Element Model implementation depth**
   - What we know: Mixed-language text needs span-level annotation.
   - Recommendation: In Phase 1.1, add language + script_variant to FormattingAnnotation. Full TextSpan implementation can be Phase 2 when extractors need it.

5. **color_semantic validation**
   - What we know: color_semantic is a free-form string ("gemara_text", "mishnah_text")
   - What's unclear: Should these be enumerated or free-form?
   - Recommendation: Free-form string for now. The semantic meanings are domain-specific (Koren has different meanings than other colored texts). Enumeration is premature. Document recommended values in schema guide.

6. **Register-level typeface_convention vs FormattingAnnotation.script_variant**
   - What we know: LayoutRegister.typeface_convention describes the EXPECTED typeface for the register. FormattingAnnotation.script_variant annotates the ACTUAL script variant per span.
   - Recommendation: Both coexist. Register declares the convention; formatting annotates the reality. They can differ (e.g., a quote in square Hebrew within a Rashi-script register). This mirrors how LayoutRegister.language is the default but FormattingAnnotation.language can override per span.
