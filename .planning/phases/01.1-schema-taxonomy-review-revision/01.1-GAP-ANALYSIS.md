# Phase 1.1 Gap Analysis: Schema vs Structural Phenomena

**Date:** 2026-02-19
**Corpus:** ~5,272 pages, 15 texts, ~85 distinct phenomena in 9 categories (139 instances across texts)
**Schema version assessed:** Post-Phase 1.1 (v2.0.0) -- all 5 plans

**Methodology:** For each structural phenomenon in the DifficultTexts catalogue, determine which Phase 1.1 schema model, field, or enum value represents it. Rate coverage as Full/Partial/None/Implicit. Rate gaps by severity: blocking (cannot represent at all), degraded (representable with workarounds via tags/extra fields), nice-to-have (improvement but not required for correctness), or N/A (no gap).

**Key distinction:** This analysis separates SCHEMA gaps (what annotators can mark) from EXTRACTOR gaps (how automated tools detect phenomena). The schema defines representational capacity. Detection is a Phase 2 concern.

### Gap Details

**1.1 / 1.4 -- Column identity and parallel reading streams**

The schema can represent two regions on the same page with independent bboxes, and Region.children allows sub-region nesting. However, there is no explicit concept of "column identity" or "register." Two column regions on the same page cannot be explicitly marked as belonging to different parallel reading streams (e.g., "Hegel column" vs "Genet column" in Glas, or "left column" vs "right column" in Tympan).

**Current workarounds:**
- Region.tags can carry `["column:left"]` or `["register:hegel"]` (tags are `list[str]`)
- GTElement.extra="allow" permits adding `column_id: str` or `register: str` as extra fields
- Region.semantic_labels can annotate the semantic purpose
- Commentary.source identifies which commentary layer a region belongs to

**What would fix it:** A `register_id: str | None` field on Region, or a document-level `Register` model mapping register IDs to metadata (author, reading direction, language). This is a nice-to-have enhancement that could be added via extra fields now and formalized in Phase 1.2 if needed.

**Assessment:** Degraded, not blocking. Annotators CAN represent the column structure spatially (bbox) and semantically (tags, extra fields). The information is representable; it lacks first-class modeling. The primary use case (evaluating column detection) works via bbox IoU regardless.

### Gap Details

**3.1 / 3.2 / 3.3 -- Typeface-as-register-signal**

The schema can annotate formatting properties (bold, italic, etc.) and language per span, but cannot express "this region uses Typeface A (which signifies Author X)" directly. FormattingType covers decorative properties but not typeface identity or point size.

**Workarounds:**
- Region.tags: `["author:bennington", "typeface:serif-9pt"]`
- GTElement.extra="allow": `{"typeface_family": "serif", "point_size": 9.0}`
- FormattingAnnotation.extra: custom typeface metadata per span

**Assessment:** Degraded. The semantic information CAN be captured via extra fields and tags. For ground truth purposes, the annotator marks WHAT the typography means (via tags or Commentary.source), not the exact font metrics. Font metric extraction is an extractor concern.

**3.7 -- Multi-typeface semantic encoding (Rashi script vs square Hebrew)**

The schema lacks a way to distinguish script variants within the same language. FormattingAnnotation.language can tag "he" (Hebrew), and BCP 47 does support script subtags (e.g., "he-Hebr" for square Hebrew), but there is no standard BCP 47 subtag for "Rashi script" specifically. The distinction between Rashi script and square Hebrew is a font/typeface distinction, not a language or script-system distinction.

**Workarounds:**
- FormattingAnnotation.language="he-Hebr" for square, with extra field `{"script_variant": "rashi"}` for Rashi script
- Region.tags: `["script:rashi"]` or `["script:square"]`
- Commentary.source already identifies who wrote the text (Rashi, Tosafot), which correlates with script type

**Assessment:** Degraded. BCP 47 covers the language and script system but not font variants. The semantic meaning (which commentator wrote it) IS captured via Commentary.source. The visual distinction (which script) requires extra fields. Not blocking because annotators can represent it; it lacks first-class modeling.

**3.9 -- Color-coded textual elements**

FormattingType has no COLOR value. The Koren Talmud uses color to encode semantic categories, but there is no way to annotate "this span is colored red" in the schema.

**Workarounds:**
- FormattingAnnotation with extra field: `{"color": "#FF0000", "color_semantic": "gemara_text"}`
- Region.tags: `["color:red", "color-meaning:gemara"]`

**Assessment:** Nice-to-have. Color as semantic signal is specific to one text in the corpus (Koren). The information can be captured via extra fields. Adding a COLOR FormattingType or a color field on FormattingAnnotation would be a minor enhancement but is not needed for correctness.

### Gap Details

**5.5 / 5.8 -- Rashi script vs square Hebrew**

Covered in Category 3 analysis (phenomenon 3.7). The Commentary.source field identifies the commentator, which correlates with script type. BCP 47 language tags cover the language. The script variant (Rashi vs square) requires extra fields.

**5.6 / 5.7 -- Text directionality (RTL/LTR/bidi)**

The schema has no explicit `text_direction` field on Region or Page. BCP 47 language tags implicitly indicate directionality (Hebrew = RTL), but:
- No way to explicitly annotate base direction at region or page level
- No bidi handling metadata (e.g., "this region is RTL with LTR numerical insertions")

**Workarounds:**
- FormattingAnnotation.language="he" implies RTL
- Region.extra: `{"text_direction": "rtl"}`
- PageGT.extra: `{"base_direction": "rtl"}`

**Assessment:** Degraded. Text direction is derivable from language tags in most cases. Explicit bidi metadata would be useful for evaluation (measuring whether extractors preserve correct reading direction) but is not blocking for annotation. Most bidi handling is an extractor/rendering concern. An annotator marks the language; the consumer derives direction.

**Does BCP 47 cover script variants?** BCP 47 supports script subtags (e.g., "he-Hebr" for Hebrew in Hebrew script). However, there is no standard subtag for "Rashi script" specifically because BCP 47 tracks script systems (Hebrew, Latin, Arabic), not font variants within a script system. Rashi script and square Hebrew are both "Hebr" script. The distinction is typographic, not linguistic.

### Gap Details

**6.6 -- Catchword anchoring (Dibbur Ha-Matchil)**

The Commentary model can represent catchword anchoring: `passage_ref` holds the catchword text, `reference_system=CUSTOM`. However, there is no dedicated "catchword" or "dibbur_ha_matchil" mechanism. The catchword is a specific kind of passage reference that uses verbatim text matching (not coordinates like Stephanus/Bekker).

**Workarounds:**
- Commentary.passage_ref = "ד״ה כל כתבי" (the catchword text)
- Commentary.reference_system = CUSTOM
- Commentary.extra: `{"anchor_type": "catchword", "catchword_text": "..."}`

**Assessment:** Nice-to-have. The Commentary model handles catchword anchoring adequately via passage_ref. A dedicated `anchor_type` field or `CATCHWORD` reference system value could improve clarity but is not needed for correctness. The annotator CAN represent the phenomenon.

### Gap Details

**7.6 / 7.7 -- Back-of-book index**

SpatialLabel has TOC_AREA but no INDEX_AREA. A back-of-book index is structurally distinct from a TOC: it lists terms alphabetically with page references, not chapters sequentially. Currently, an index region would need to use TEXT_BLOCK or UNKNOWN.

**Workarounds:**
- SpatialLabel.UNKNOWN for the region + Region.tags: `["index_area"]`
- DocumentStructure.back_matter can hold index metadata
- GTElement.extra: `{"spatial_subtype": "index_area"}`

**Assessment:** Nice-to-have. Only 2 texts in the corpus have significant indexes (Of Grammatology pp. 413-444, Being and Time pp. 575-590). The UNKNOWN label + tags adequately represents it. Adding INDEX_AREA to SpatialLabel would be a minor, non-breaking addition.

**Is there a distinction between TOC and INDEX needed?** Yes, they differ:
- TOC: sequential document structure, hierarchical, located at front
- INDEX: alphabetical term listing, flat or two-level, located at back
For layout detection evaluation, they have different visual patterns. However, both are relatively rare per-document (one instance each), so the evaluation impact is minimal.

**7.9 -- Domain-specific section types (parashah, tractate, perek)**

There are no domain-specific section type values in any enum. The Section model has a generic `title` and `level` but no `section_type` field for domain categorization.

**Workaround:** Section.extra: `{"section_type": "parashah", "parashah_name": "Bereishit"}`. GTElement.extra="allow" handles this cleanly.

**Assessment:** Not a gap -- this is exactly what extra fields are for. Domain-specific categorization should NOT be hard-coded into the universal schema. Each project/corpus adds its own section taxonomy via extra fields or tags.

### Gap Details

**9.1 -- Handwritten annotations**

The schema can flag pages with handwritten overlays via PageQuality.artifacts but has no model for representing the annotations themselves (location, content, distinction from printed text).

**Workarounds:**
- PageQuality.artifacts=["handwritten_overlay"]
- Region with SpatialLabel.UNKNOWN + tags=["handwritten_annotation"]
- Region.extra: `{"annotation_type": "handwritten", "ink_color": "blue"}`

**Assessment:** Degraded. Handwritten annotations appear in only one text (Margins of Philosophy, 4 pages). For GT purposes, the primary need is to FLAG these pages so extractors know to handle the overlay, which PageQuality.artifacts does. Modeling the annotation content is a future enhancement.

**9.3 -- Mathematical and symbolic notation**

SpatialLabel.FORMULA handles region-level math blocks. FormattingAnnotation with SUPERSCRIPT/SUBSCRIPT handles inline notation. However, there is no inline FORMULA or MATH formatting type for embedded mathematical expressions within running text (e.g., "E = mc^2" within a paragraph).

**Workarounds:**
- FormattingAnnotation with extra: `{"content_type": "math_inline"}`
- Region.tags: `["contains_math"]`

**Assessment:** Nice-to-have. Mathematical notation appears in one text (Gibbs) and is relatively sparse. The FORMULA spatial label for blocks and SUPERSCRIPT/SUBSCRIPT for inline elements cover most needs. Inline math rendering is typically an extractor/output concern.

**9.7 -- Intentional parallel enrichment**

The concept of "reading two registers simultaneously for enriched meaning" is an interpretive/analytical concept, not an annotatable structural phenomenon. The schema represents the parallel structure (two registers) but not the semantic relationship "these are designed to be read together."

**Workarounds:**
- DocumentGT.extra: `{"reading_mode": "parallel_enrichment"}`
- Region.tags: `["parallel_pair:circumfession"]`

**Assessment:** Nice-to-have. This is a document-level literary analysis observation, not a structural annotation need. The schema represents the physical parallel structure; the enrichment interpretation is downstream.

## Phase 1.2 Recommendation

### Verdict: Conditional -- Phase 1.2 is beneficial but NOT required for Phase 1.1 execution to proceed.

**Rationale:**

1. **Zero blocking gaps.** Every structural phenomenon in the corpus can be represented in the Phase 1.1 schema. No annotator will encounter a phenomenon they cannot mark.

2. **All degraded gaps have immediate workarounds.** The GTElement.extra="allow" design decision (made in Phase 1) provides a forward-compatible escape hatch. Every "degraded" gap can be addressed by adding extra fields to the relevant model instances. This is not a hack -- it is the designed extensibility mechanism.

3. **The schema is designed for progressive annotation.** Not everything needs first-class modeling from day one. The pattern is: start with extra fields, observe usage patterns, promote frequently-used extras to formal fields in a later schema revision.

4. **Some gaps are extractor/pipeline concerns, not schema concerns.** Text direction detection (G5), handwritten overlay handling (G9), synchronized column analysis (G8), and parallel enrichment interpretation (G11) are better addressed in Phase 2 (Extractor Interface) or Phase 4 (Annotation Tool), not by adding more schema fields.

5. **The corpus-specific gaps are narrow.** Color-coded text (G4) appears in 1 text (Koren). Handwritten annotations (G9) appear in 1 text (Margins, 4 pages). Inline math (G10) appears in 1 text (Gibbs). Rashi script distinction (G3) is relevant to 2-3 texts. These are niche phenomena in a 15-text corpus.

### If Phase 1.2 is undertaken, recommended scope:

**High value (address the 5 degraded gaps):**

1. **Text direction field** -- Add `text_direction: Literal["ltr", "rtl", "bidi"] | None` to Region. Low effort, high value for Hebrew/Arabic text evaluation.

2. **Script variant annotation** -- Add `script_variant: str | None` to FormattingAnnotation for cases where BCP 47 is insufficient (e.g., Rashi script). Or extend FormattingType with SCRIPT_CHANGE.

3. **Register/column identity** -- Add `register_id: str | None` to Region and a document-level RegisterSchema model mapping register_ids to metadata (author, language, reading_direction).

4. **Typeface annotation** -- Add FONT_CHANGE or TYPEFACE to FormattingType, with extra fields for font_family, point_size. Or create a lightweight FontAnnotation model.

5. **Handwritten overlay flag** -- Extend PageQuality or Region to distinguish printed vs handwritten content layers. Minimal: `content_layer: Literal["printed", "handwritten"] | None` on Region.

**Low value (nice-to-have, consider deferring to Phase 2+):**

6. COLOR in FormattingType -- One-text phenomenon.
7. CATCHWORD in ReferenceSystem -- Already works via CUSTOM.
8. INDEX_AREA in SpatialLabel -- Already works via UNKNOWN + tags.
9. MATH_INLINE in FormattingType -- Sparse phenomenon.

### Recommendation for immediate action:

**Proceed with Phase 1.1 execution as planned.** The 5 plans are well-designed and address the primary structural tensions. No plan adjustments are needed. The gap analysis confirms that the Phase 1.1 redesign handles the vast majority of the corpus's structural complexity.

If Phase 1.2 is undertaken, it should be a focused sprint addressing items 1-3 above (text direction, script variant, register identity) as these are the most broadly applicable gaps affecting the Hebrew/Aramaic texts (which represent ~30% of the corpus pages). Items 4-5 are lower priority and could be deferred further.

The extra="allow" mechanism provides adequate interim coverage for all identified gaps. No annotator or evaluator will be blocked.
